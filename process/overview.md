# ToB 产品 Agentic 全流程概览

[English](overview.en.md)

> 本文档是 PM Agentic Cookbook 的核心导航，指引 PM 按阶段完成从需求到上线的全流程。

---

## 流程总览

```
Source Intake → Domain Model → Acceptance Criteria → PRD Draft → PRD Audit → UI Prototype → Test → Requirements Acceptance & Final Verification
   阶段零          阶段一           阶段一后          阶段二      阶段三        阶段四      阶段五                      阶段六
```

**阶段零决定后面各阶段的依据从哪来。** 它判断手上有什么材料、够不够支撑后续设计。原流程图起点的「业务依据」不是凭空出现的输入——它是阶段零的产出。

---

## 阶段门禁规则

每个阶段都采用"阶段产出 + AI 自审 + 用户审查 + 明确确认后推进"的门禁机制。

执行约束：
- 每个阶段完成后必须停下来，不自动进入下一阶段。
- 阶段内允许多轮修改，直到 AI 自审和用户审查都通过。
- 用户未明确确认前，不推进下一阶段。
- 所有业务依据必须来自项目内已确认的来源文档。
- **系统解决方案（或项目已确认来源文档）是唯一实现依据**：不得擅自更改其功能实现逻辑；确需偏离时停下交用户裁定，而非自行改写来源逻辑。
- **发现底层数据层断裂/缺失、与来源文档实现逻辑不一致时，禁止擅自砍链路或砍掉中间层做降级实现**：停下明确告知用户，由用户决定是否补齐数据层，再继续。降级会让实现悄悄偏离来源文档，并沿 PRD/原型层层放大。
- **严守 Domain Model → 验收标准 → PRD 顺序，不本末倒置**：PRD 必须基于已完成且正确的数据建模生成；一旦发现 PRD 底层逻辑缺失或错误，先回查并修正 Domain Model，确认模型后修订受影响验收条目并交用户确认，再同步PRD。
- **全流程回流**：任一下游阶段发现上游缺漏、冲突或不可实现时，暂停受影响工作并回改最上游产物，不在下游自行换口径；涉及验收清单的行改为待确认、变更记录注明来源阶段。用户确认后逐项同步PRD、覆盖清单和测试引用并重新验证，旧结果不证明新口径。审计/走查者只记录问题，回改由获得修改授权的作者执行。
- **流程入口一律是阶段零 Source Intake**，档位判定决定 Oracle 的来源，不裁剪后续阶段。跳过阶段零直接进建模，等于默认"材料一定够"，而这个假设从来不会自己报错。
- 不跳过数据建模、PRD、审计直接写 UI。
- 不跳过测试阶段直接进入最终验证：原型代码必须以 PRD 为预言(oracle)接受可执行测试,把"实现与 PRD 的偏差"显性化为测试用例与测试报告。
- 测试结果如实记录,失败项分类为「实现缺陷」或「PRD/Mock 口径待确认」,**是否通过、是否推进由用户裁定**,AI 不自我宣告"测试通过"。
- 最终验证通过后，再考虑 commit、push、PR。
- **作者不得审计自己的产物**：由 AI Agent 执行流程时，PRD 审计（阶段三）、照单 E2E 走查与旅程审计（阶段五）必须委派独立子代理执行；每个阶段的执行者、子代理派发 checklist 与修复权限边界见 `process/agent-execution-protocol.md`。

## 需求范围与产物归集

需求范围是一组有明确业务结果、包含/排除、依赖契约和有意义验收出口的需求。每个经用户最终确认的范围维护一份标准清单及一份对应验收台账；同一范围可关联多份Domain Model和PRD，共享模型可供多个范围引用。模型按业务对象组织，文件数、页面数、模块名和用户一轮输入都不能单独决定范围数。

阶段零逐项对照原始输入，整理候选范围及未决交叉点，交用户确认初步边界；建模阶段验证实体、状态、规则和依赖，提出必要的合并/拆分或依赖调整；标准生成前由用户最终确认范围名称、业务结果、包含/排除、依赖和验收出口。最终确认可并入已有模型确认节点，已明确确认的不重复询问。后续范围变化先交用户确认，再同步模型、清单、PRD和台账，不能按实现现状缩小要求。

复用需求确认书或现有模块/项目入口的范围表：`范围名称｜业务结果｜包含与排除｜依赖与交叉｜验收出口｜确认状态`。独立结果分别闭环；共同支撑一个不可拆结果时保留一个跨模块范围；独立结果另有共同端到端要求时增设仅覆盖共同条件与交互结果的集成验收范围，具名引用共享契约和子范围版本，不复制子范围标准。子范围通过不能证明集成出口通过。边界不足以判断时交用户裁定，不能遗漏原始要求或代为确认。

模块入口只保留轻量索引：`范围名称｜关联模型/PRD｜标准清单｜验收台账｜当前进度`。跨模块范围明确唯一主归集位置及协调责任方，其他模块索引同一组产物；无适用主模块时由调用方指定项目级落点。同一范围连续迭代沿用原清单与台账；拆分/合并经用户确认后保留旧范围和条目到新归属的映射，旧编号和历史不消失。

标准清单是业务定义，当前正文保留定义、确认/作废状态和简要变更记录。台账是宿主过程记录，当前视图只呈现有效结果、未闭环事项和轮次索引；已结束轮次完整记录保存在可定位的历史快照，避免累积旧全文。台账按调用方明确的范围前缀保存于主归集模块的`host.processRecordsDir`；模块目录来自`host.moduleDocs`，不自行猜位置。标准定义确认与交付验收分别记录，未验收不改变已确认标准的状态。

## 阶段零：Source Intake（源材料准入）

**目标**：在建模之前判断材料是否支撑设计，确定Oracle来源并初划可交付需求范围；档位不裁剪后续阶段。

**为什么这一步在最前面？**
后续每个阶段都以「存在一份质量足够的 Oracle」为前提：生成 PRD 要有依据，审计要有比对基准，写测试要有预言。**这个前提从来不会自己报错**——材料缺失时，各阶段照常产出看起来完整的文档，只是那些文档没有判据。阶段零把这个前提变成一次显式检查。

**核心裁定**：**Oracle 必须存在，且必须是文件。** 差别只在它从哪来——用户提供的文档、访谈固化成的确认书、或从运行中的系统反向工程出的基线。**没有 Oracle 的项目不接。**

**操作步骤**：

1. 加载 `skills/source-intake/SKILL.md`。
2. 执行**准入四问**：可读性 → 权威性 → **完备性（广度 × 深度）** → 一致性。四问全部有结论才进入下一步。
3. **判定档位** T0–T3，决定 Oracle 来源。判定结论交用户确认。
4. 材料不足时（T0/T1）执行**结构化访谈**，把需求固化成《需求确认书》并附完备度矩阵（用户确认 / 执行者推断 / 仍空白）。
5. 已有运行中系统时（T3）反向工程出《现状基线》，每条结论带可信度标签与证据指针。
6. 逐项整理候选范围、交叉依赖与未决边界，复用范围简表交用户初步确认；把 UNRESOLVED 清单交用户裁定；**AI 不得自行宣告准入通过**。

**产出物**：

- [ ] 《源材料准入报告》（四问结论 + 档位判定 + 广度/深度缺口 + UNRESOLVED 清单 + 能力边界声明）
- [ ] 《源材料索引》——后续所有阶段查阅材料的**唯一入口**
- [ ] 《需求确认书》+ 完备度矩阵（T0/T1）
- [ ] 《现状基线》（T3）

**落地要求**：

- **后续阶段不得手工遍历材料目录**，一律经《源材料索引》按锚点定位。
- 材料在过程中变化（补交文档、发现覆盖不足）时，**重新走四问并更新档位**，不沿用旧判定。
- 访谈产出是**待确认草稿**，不是权威需求——最有效的业务理解手段（观摩、轮岗、进入作业现场、建立信任）AI 一项都做不到，这条局限必须在报告中声明。

## 阶段一：Domain Model

**目标**：将模糊的业务诉求转化为精确的、结构化的数据模型。

**为什么这一步至关重要？**
ToB 产品的核心复杂度在数据层。薪酬计算、预算编制、审批流转——这些都依赖于严谨的数据关系。
如果数据模型不清晰，后续 AI 生成的 PRD 和原型都会"失真"。

**操作步骤**：
1. 以阶段零的产出为输入：T2/T3 用《源材料索引》定位材料，T0/T1 用《需求确认书》。**不再从零收集需求**——那是阶段零的职责
2. 将需求喂给 AI，配合 `skills/domain-modeling/SKILL.md` 指令
3. AI 将输出：ER 关系图、核心实体定义、字段规范、计算链路
4. AI自审并运行Mermaid校验，以模型验证候选范围的业务出口、共享实体与依赖；必要调整交用户确认，不为验收分组拆造实体
5. 用户确认模型与最终需求范围后进入验收标准阶段；范围可引用多份模型，清单逐条确认后才进入PRD Draft

**产出物**：
- [ ] Domain Model 文档
- [ ] 核心实体清单与字段定义
- [ ] ER 关系图与关系明细表
- [ ] 业务规则与计算链路
- [ ] 自审清单

---

## 阶段一后：Acceptance Criteria（验收标准）

**目标**：把已确认模型及需求依据转成可由用户逐行核对的业务完成标准。

1. 使用 `skills/acceptance-criteria/SKILL.md`，提供最终已确认范围、需求依据、所有关联已确认模型版本、清单路径和对应台账落点。
2. 输出文首范围/依据/状态、分节五列主表（编号、场景、预期结果、来源、状态）、待确认清单和变更记录。一行只核一件事；来源为文档名、章节号与节名，状态只有待确认/已确认/作废，编号只增不复用。
3. 用户逐条确认，生成草稿即停下；未确认或存在上游冲突时不进入PRD。
4. 下游引用清单名称加编号，不复制权威主表。PRD细化页面断言；journey-audit阶段A和test-authoring分别产出旅程与测试数据。

**产出物**：具名、可追溯的验收清单、待确认事项与变更记录；与PRD、覆盖清单、测试的一致性由consistency-audit核对。

---

## 阶段二：PRD Draft

**目标**：基于已确认Domain Model与验收标准清单，生成PRD初稿。

**操作步骤**：
1. 将已确认模型和逐条确认的验收标准清单作为输入；第4.2节引用清单，第10.2.1.4每行具名引用所细化的标准
2. 使用 `skills/create-prd/SKILL.md` 指令，让 AI 生成完整 PRD
3. AI 按章节完整性、图表、流程、状态机、异常处理自审
4. 用户确认 PRD Draft 后，才能进入 PRD Audit

**产出物**：
- [ ] 结构化 PRD 文档
- [ ] PRD 自审清单

---

## 阶段三：PRD Audit

**目标**：对 PRD 执行质量审计，输出问题分级和修正建议。

**操作步骤**：
1. 将阶段二产出的 PRD 作为输入
2. 使用 `skills/check-prd/SKILL.md` 指令审计 PRD
3. 按 P0/P1/P2/P3 分级输出问题和修正建议
4. 审计报告回收后，由主 Agent 把未关闭的问题登记进模块的问题登记表（模块过程记录目录下的 `<module>_open_findings.md`，目录名见宿主契约的 `host.processRecordsDir`），报告原文随本轮提交入库后删除；用户只需读登记表
5. 用户确认无阻塞问题后，才能进入 UI Prototype

**产出物**：
- [ ] PRD 审计报告
- [ ] 同路径历史审计报告处理清单
- [ ] P0/P1 处理结论
- [ ] P2/P3 延期或接受说明

---

## 阶段四：UI Prototype

**目标**：从已审计 PRD 生成可交互的高保真前端原型。

**操作步骤**：
1. 将 PRD、审计结论和 ui-generator 的 `templates/tob_design_tokens.css` 一起作为输入
2. 使用 `skills/ui-generator/SKILL.md` 指令
3. 复杂表格场景结合 `skills/table-template-designer/SKILL.md`
4. 本地 `npm run dev` 预览并迭代
5. 用户确认页面体验和业务闭环后，才能进入测试(Test)阶段

**产出物**：
- [ ] 可运行的高保真原型
- [ ] 组件化前端代码
- [ ] 用户走查反馈处理结果

---

## 阶段五：测试(Test)

**目标**：把"原型实现与 PRD 之间的偏差"从不可见变为可裁定——以 PRD 为预言(oracle),对实现施加可执行测试,并产出测试用例文档与测试报告。

**为什么需要独立的一阶段？**
没有测试环节时,AI 基于 PRD 写出的代码与 PRD 之间的偏差对用户不可见;走查只能抽样、无法回归。测试阶段让偏差显性化、可回归、可追溯,是"实现回归到 PRD"的闭环。

**操作步骤**：
1. 加载 `skills/test-authoring/SKILL.md`,以 PRD 的结构化内容为测试用例来源:业务规则(事实/约束/触发条件/推论/计算)、已确认的独立验收标准及其PRD细化、状态机、异常处理方案、角色权限矩阵。
2. 按测试金字塔分层落地可执行测试:纯函数/派生逻辑→单元测试;状态流转与跨实体规则→集成测试;关键页面→组件测试。期望值取自 PRD 口径,而非照抄实现。
3. 运行测试(如 `npm run test:run`),产出:
   - **测试用例文档**(test-authoring 的 `templates/tob_test_case_spec.md`):用例编号、具名PRD章节、验收标准（清单名称加编号）、步骤、预期、结果；逐标准登记已覆盖或未覆盖原因。
   - **测试报告**(test-authoring 的 `templates/tob_test_report.md`):通过/失败汇总 + 失败缺陷清单(含 P 分级与裁定列)。
4. 失败项如实分类为「实现缺陷」或「PRD/Mock 口径待确认」;AI 不自我宣告"测试通过"。
5. 已声明功能/迭代范围完成开发与测试后做阶段回看，更新对应台账的核对结果及缺口，不自动宣告最终验收。用户裁定后进入需求验收与最终验证，或将偏差回流到最上游缺漏所在阶段；模型/验收口径先修订并确认，再同步PRD、UI与测试。

**产出物**：
- [ ] 可执行测试套件(单元/集成/组件)
- [ ] 测试用例文档(追溯到 PRD)
- [ ] 测试报告(通过/失败 + 缺陷分级 + 裁定列)
- [ ] 失败项分类与回流/修复结论

**落地要求**：
- 测试以 PRD 为预言:测试失败优先视为"实现或口径的真实发现",而非改测试迁就实现。
- v1 可不追求覆盖率,但必须真实可跑、可回归,并输出用例文档与报告(贴近真实测试环节)。

## 阶段六：需求验收与最终验证（Requirements Acceptance & Final Verification）

**目标**：开发、测试与必要走查完成后，逐条核对交付是否达到已确认标准，提供证据和未闭环事项，由用户明确验收本期范围。

**操作步骤**：
1. 固定已确认需求范围、本期包含/排除、标准清单版本、实现版本和证据基线，校验构建及运行。排除项须有明确范围确认；待确认/缺漏标准作为前置缺口回流，不能跳过后宣告整体验收。
2. 使用[需求验收台账模板](../templates/tob_acceptance_register.md)，每个范围维护一份台账，列齐本期适用标准及其余条目的归属；正常、异常、权限、边界和有依据的非功能要求均须核对。集成范围单独核共同出口，未就绪依赖不能用Mock证明真实闭环。
3. 复用当前有效测试、真实走查及独立审计证据，查实际断言、路径、版本与未覆盖边界。测试全绿或页面已做不能替代逐标准证据；单元测试不自动覆盖旅程/集成，旧版本证据不证明新语义。需要独立一致性核对时按对象/问题路由，纳入既定Task收尾审计或复用有效结论；进入阶段六不自动增加全量审计。
4. 填四档核对结果、证据和未闭环事项，反查实现/测试中是否存在无标准依据的业务行为。确定缺陷修复后重验，标准有错先回改最上游依据并重新确认；不能降低标准求绿。
5. 将逐条结果、证据、未闭环事项及本期范围交用户验收。用户可明确批量裁定一个范围，执行者仅更新该范围；其他条目的用户结论留空。明确本次交付结论后进入后续交付/协同，例外与延期继续可见。

**核对结果与用户结论**：台账主表为`验收标准（清单名称＋编号）｜核对结果｜证据｜未闭环事项｜用户验收结论`，不复制标准主表。尚未核对的结果留空并注明待核对；核对后只用下列四值：

| 核对结果 | 判据 |
| --- | --- |
| 满足 | 本期声明范围内全部必要适用路径有当前充分证据支持，未发现反例 |
| 部分满足 | 同一标准的部分适用路径已证满足，另有路径已证未满足；两侧均须定位 |
| 不满足 | 有确定反例，且无已证满足范围构成“部分满足”；未知范围同时保留 |
| 证据不足 | 缺当前、相关且充分的证据，无法建立前三种判断；已测成功、其余未测归此类 |

部分满足不降低安全/权限等失败的风险等级。用户验收结论只据明确裁定填写，可记通过、不通过、接受偏差或延期，附日期与依据。满足加用户明确通过，才核销本版本/范围的验收事项；满足但未裁定仍待验收。接受偏差保留原事实结果、例外边界和后续安排，不改成满足；延期保留未完成事实。原清单仍用待确认/已确认/作废，验收通过不删除标准或回收编号，作废不计通过。

**阶段回看与变更重验**：已声明功能/迭代的开发测试完成，或语义变化影响旧结论时，按上述证据核对更新台账并限定本期范围；普通保存不产生新轮次。受影响条目重新核对和获得验收结论。无影响结果继承须有语义及实现无影响的证据，旧用户结论保留原范围/版本/日期，只作历史；本期是否沿用仍由用户明确确认。台账汇总分别列适用总数、四档数/未核对数、用户裁定数/未裁定数，不把部分、偏差、延期或不适用加入全部满足。

## 💡 最佳实践

1. **"写一做一"同步法**：每完成一个模块，立即回顾总结与 AI 的协作过程
2. **数据模型先行**：永远在写 PRD 之前完成数据建模
3. **小步快跑**：每个页面单独生成、单独验证，不要一次性提交所有需求
4. **保留 Prompt 日志**：记录每次与 AI 交互的关键 Prompt，持续优化指令质量
5. **诊断先行、修复与设计决策分流**：面对混合型问题清单，先全量定位 + 逐条根因诊断（定位到 `file:line`），把每条分类为「确定性修复」或「设计待定项」；确定性修复直接做，设计待定项作为**显式选项交用户裁定后再编码**，不在未定方向上擅自实现
6. **数据层断裂即停、不降级**：数据建模/PRD 阶段发现底层数据层断裂或缺失（如缺中间层实体、断链），宁可停下补数据、回改 Domain Model，也不在缺失的中间层上做降级实现——降级看似"能跑通功能"，实则已偏离来源文档，且沿 PRD、原型放大。是否补齐数据层由用户裁定，AI 只诊断并交决策
