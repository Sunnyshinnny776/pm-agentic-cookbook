# Agent 执行协议（机器可执行层）

> `process/overview.md` 是面向 PM 的流程说明书；本文档是面向 **AI Agent** 的执行协议，
> 规定每个阶段由谁执行、子代理如何派发、裁定权归属。两者冲突时以本协议 + 用户当轮指令为准。

---

## 1. 角色定义

- **主 Agent（编排者/作者）**：与用户对话的 Agent。负责按 `process/overview.md` 推进阶段、
  生产产物（Domain Model、PRD、原型代码）、派发子代理并回收其报告。
- **审计子代理（独立审计者）**：没有参与被审产物修复的 Agent。首次审计和完整重审使用
  fresh auditor；定向复审可复用上一轮独立审计者，但必须重新读取当前 artifact 与 Oracle，
  不得只继承作者摘要或旧结论。

**核心不变量：作者不得审计自己的产物。** 主 Agent 是作者时，Task 收尾审计、必要的 P0/P1
定向复核和契约变化后的全量重审均由独立审计子代理执行；作者侧机械检查、测试、代码缺陷自查
与修复由主 Agent 执行。主 Agent 不得修改、稀释或代写独立审计结论。

**Task 的边界由目标、Oracle、交付范围与完成点定义。** 文件保存或一次修复不构成新的 Task；
进行中的验证不触发独立审计。整体完成并通过作者侧验证后，按第 6 节执行一次收尾审计。

## 2. 阶段 × 执行者矩阵

| 阶段 | Skill / 动作 | 执行者 | 说明 |
| --- | --- | --- | --- |
| 零 Source Intake | source-intake | 主 Agent + 用户 | 候选范围及交叉依赖初划，由用户初步确认 |
| 一 Domain Model | domain-modeling | 主 Agent | 作者身份 |
| 一后 Acceptance Criteria | acceptance-criteria | 主 Agent | 模型及最终需求范围确认后，每范围一组清单/台账；标准逐条确认后才进PRD |
| 二 PRD Draft | create-prd | 主 Agent | 作者身份 |
| 三 PRD Initial Audit | check-prd initial audit | **fresh 审计子代理（必须）** | 主 Agent 是作者时不得自审；完整执行适用维度 |
| 任一阶段 · 一致性审计 | consistency-audit | **fresh 审计子代理（必须）** | Task 收尾审计含两类以上被审对象时使用；触发点见 6.3，标准路由见 6.2 |
| 任一阶段 · Focused Recheck | 按 6.2 所选 skill 的 focused recheck | **独立审计子代理（必须）** | P0/P1 修复完成后由同一审计者只核相关条目一次，并查其影响范围与邻接回归 |
| 任一阶段 · Full Re-audit | 按 6.2 所选 skill 的 full re-audit | **fresh 审计子代理（必须）** | 修复改变契约、模型或范围时；fresh 实例重新建立完整结论 |
| 四 UI Prototype | ui-generator / table-template-designer | 主 Agent | 作者身份 |
| 四/五 · 代码缺陷自查 | 宿主提供的代码审查能力；没有时用写代码 skill 自带的清单 | 主 Agent | 作者侧质量动作：发现即修、向用户简述，**不出报告、不属审计**；完成后才算修复批次完成 |
| 五 Test · 代码层 | test-authoring | 子代理（建议） | 测试作者独立于实现作者更可信 |
| 五 Test · 覆盖清单 | journey-audit 阶段A(plan) | 主 Agent 或子代理 | 从 PRD 派生清单，无作者偏差 |
| 五 Test · 照单走查 | 浏览器 E2E 走查（模板见 4） | **走查子代理（必须）** | 代替/辅助人工照单测试 |
| 五 Test · 旅程审计 | journey-audit 阶段B(run) | **审计子代理**（主 Agent 是原型或 PRD 的作者时必须） | 审计者独立于原型作者与走查执行者 |
| 六 Requirements Acceptance & Final Verification | 构建/走查证据 + 范围级验收台账 | 主 Agent + 用户 | 作者逐标准核对证据，用户明确验收；不自动增加全量审计 |

下游发现上游缺漏时暂停受影响工作，回改最上游依据并交用户确认，再同步引用和验证。验收标准清单保持唯一权威，PRD、覆盖清单与测试用清单名称加编号引用。审计/走查只记录缺口，不获得修订上游的权限；作者只在既有任务授权内修订，不代用户确认。

范围在阶段零初划、建模验证、标准生成前最终确认；跨模块范围须指定主归集位置和协调责任方。一个范围可引用多模型/PRD，共享模型保持唯一来源。需求范围用于归集业务产物，Task仍按目标、Oracle、交付范围和完成点定义；清单/台账数量不增加审计次数。

阶段性回看及正式验收由作者复用当前测试、真实走查与有效独立证据，按[流程](overview.md)和[台账模板](../templates/tob_acceptance_register.md)逐条记录满足/部分满足/不满足/证据不足。用户明确通过且核对满足才核销本版本/范围；偏差与延期保留事实和后续事项，未裁定留空。标准确认、事实核对、用户交付验收分开。需要独立核对时沿用6.2/6.3路由与Task收尾触发；审计者只读并报告，不更新台账或替用户验收。

## 3. 子代理派发 checklist（冷启动必给项）

子代理没有会话历史，派发 prompt 缺项会导致其乱找文件、自行假设。派发前逐项核对：

> **审计一律按对抗式审查派发。** 审计子代理的任务是**证伪**，不是确认。默认立场是「这批产物有问题，我要找出来」，
> 而不是「看起来没问题，通过」。这不是态度问题，是取证方向问题——以确认为目标的审查只会去看作者已经写好的地方，
> 而缺陷恰恰藏在作者没写的地方。派发 prompt 必须把这个立场写成明文指令，不能指望子代理自己领会。

1. **使用的 skill**：按 6.2 路由表选择，明确指令加载哪个 skill。一次 Task 收尾审计要回答多个问题时，按各对象和问题列出适用标准，在同一次收尾审计中覆盖；不因问题数量另增审计轮次。
2. **审计动作与变更等级**：声明 initial audit / focused recheck / full re-audit，以及 M0/M1/M2 深度；M0 机械验证由作者执行，不因维护动作另派复审。
3. **修复批次边界**：说明本批次包含哪些已完成修改和作者侧验证；禁止在批次未完成时边修边审。
4. **被审产物与范围声明**：按 6.1 的对象类逐类列出绝对路径，不许"自己找"；Oracle 的入口文档（定位权威依据用的索引）也算被审对象。同时写明本轮**不在范围**的类，要求报告附"本轮未读清单"。
5. **Oracle**：PRD / Domain Model / specs 的绝对路径（审计判定的唯一依据）。
6. **输出位置**：本轮审计原文落盘的绝对路径，放在被审对象所在模块的过程记录目录里（见 6.10）。原文是临时的，登记完成后删除。
7. **登记表条目**：Task 收尾与全量重审给出模块登记表全部未关闭条目；定向复核同时给出指定 P0/P1 集合、影响路径与其余条目的继续登记状态。**审计者不修改登记表，不删除、不标记任何其它文件**，登记与清理由主 Agent 按 6.8 执行。
8. **Dispatch 目标**：Task 收尾审计按整个 Task 及全部遗留条目列核销目标；P0/P1 定向复核只列必须验证的高风险修复与邻接回归，其他状态按 6.7 保留；不得用 focused 名义缩小 Task 初审范围。
9. **完成标准**：报告必须包含的段落——P0–P3 分级、裁定列、覆盖度、证据定位、本轮未读清单、登记表条目核销表；回收物按 6.6 的 handoff 字段交回。
10. **禁止事项**：不得自我宣告"通过/可推进"；审计任务不得直接修改被审产物，也不得删除或标记其它报告；口径不明标注
   「待确认」交用户，不自行假设。
11. **回收物**：按 6.6 的 handoff 契约交回；主 Agent 原样转呈用户，核验实际 diff 只新增了原文文件，再按 6.8 登记与清理。
12. **中断落盘要求**：写明「若中途被中断，已完成部分先落盘到报告文件，不要只留在回复里」。中断处理见 3.2。
13. **对抗式立场的明文指令**：把下面六条写进 prompt，一条不少。它们各自对应一类常见的漏审，不是修辞。
14. **冷启动断言**：派发前确认本次派发**不包含**被审产物的作者上下文（作者的推理、自评、修复说明只能作为被审对象写进 prompt，不能作为背景事实），并在交付说明（如 PR 描述）中声明。

### 3.1 对抗式审查：写进 prompt 的六条

1. **不采信作者的任何自述状态。** 处置表里的「已消解」、变更记录里的「已修复」、任务卡里的「完成」，全部是**被审对象**，不是输入。逐条回到原文重新取证。作者写「两处都改了」而实际只改了一处，这类错误只有独立复核能抓到——**审计的价值恰恰集中在这里**。
2. **提问方式是「什么情况下它会错」，不是「它看起来对不对」。** 后者会让审查停在作者已经论证过的地方。照着合同的编号顺序走一遍、逐格比对两张表、把断言的边界值代进去，这些笨办法才是有效的。
3. **优先查作者最可能跳过的地方。** 逐格比对、计数、跨文档的同一个数、从未进入过审计范围的资产（图示、附件、旧文档）、以及「显然不会有问题」的部分。作者的疲劳点就是缺陷的聚集点。
4. **派发 prompt 本身由作者撰写，不构成事实。** prompt 里的背景说明、改动清单、甚至「重点验证事项」都可能有偏差或遗漏。要用 `git diff`、`git log` 和文件原文自己核一遍；发现 prompt 说法与事实不符，这本身就是一条发现。
5. **零发现是一个需要证据的结论**，与任何一条发现同等。若某维度确实无问题，写明取证动作与覆盖范围；不能因为没找到就略过不提。
6. **对抗不等于凑数。** 每条发现必须有证据定位与可复现的判据；不确定的写「待确认」并说明缺什么证据。制造发现和放过缺陷一样有害——前者稀释报告可信度，读者一旦发现有几条是凑的，就不再相信其余的。

**主 Agent 侧的配套义务**：派发时不得在 prompt 里替子代理下结论（「这一批应该没什么问题」「重点看 X 就行」这类措辞会直接压掉证伪动机）；回收时不得因为发现数多就要求子代理复核自己的结论。**独立结论原样转呈，异议单独提。**

### 3.2 子代理中途失败：唤醒同一个，不要重派新的

子代理因 API 错误、连接中断、配额限制提前终止是常见情况，处理方式固定：

1. **优先唤醒同一个子代理续跑。** 它的上下文还在，从自己的 transcript 接着走。重新派发一个新代理是冷启动——被审产物与 Oracle 要全部重读一遍，token 成本高，而且前后两半程可能得出口径不一致的取证结论。
2. **唤醒前主 Agent 必须先核实现场**，并把结果写进唤醒消息：工作树在它停摆期间有没有被改动、输出目录有没有留下半成品报告、HEAD revision 与未提交改动是否仍与中断时一致。子代理自己判断不了这些。
3. **唤醒消息只补差量**：现场事实 + 「其余要求按上一条派发执行」。重述整份派发合同等于人工制造冷启动，把省下来的又花回去。
4. **派发时就要求落盘**：若中途中断，已完成部分先写进报告文件，不要只留在回复里——回复随进程丢失，落盘的不会。这条写进派发 prompt 的完成标准里。
5. 同一 task-id 可能多次通知失败。每次都按第 2 步重新核实现场，不要凭上一次的结论直接唤醒。
6. **唤醒后仍失败且原因是配额、限额这类外部约束时，如实告诉用户阻塞原因与恢复时间。** 不得改用主 Agent 自审来「绕过」——那会直接破坏作者与审计者隔离，得到的结论没有独立性可言。

续做的执行者若不是同一个子代理，本节不适用，按 6.9「中断后接手的报告要标证据等级」处理。

## 5. 裁定权归属

子代理的审计/走查/测试报告是**供判断与裁定使用的证据**，不构成通过认证。
业务事实、Oracle 冲突与需要取舍的范围问题按批交用户；技术修复、审计与规定的复核按第 6 节
自行执行并告知动作、依据、结果和后续处理。任何执行者不得自行宣告“审计通过、可推进”。

Delivery actions follow the host's explicit authorization rules; this protocol grants no commit, push, PR or merge permission.

## 6. 审计体系

审计的标准由**被审对象 × 要回答的问题**决定；变更等级（M0/M1/M2）只决定审多深、由谁审。本节是派发方（主 Agent）执行的部分；每个审计 skill 自己的 `references/` 只规定审计者在该标准下做什么。

### 6.1 被审对象分类

| 类 | 是什么 |
| --- | --- |
| **需求文档** | Overview、Sub PRD、变更需求文档 |
| **数据模型** | Domain Model |
| **目录与主数据** | 被多份文档引用的唯一出处目录（权限点目录、组织树、字典、编码表等），**及其在代码里的镜像** |
| **规范** | 跨模块共用的规则文档（界面、集成、工程、安全、测试规范） |
| **验收标准清单** | 经用户逐条确认的业务完成标准，先于PRD，作为下游具名追溯依据 |
| **测试规格** | 测试用例规格、E2E 覆盖清单 |
| **图示** | 流程图、架构图及其生成脚本 |
| **Oracle 入口** | 定位权威依据用的索引 |
| **代码** | 业务逻辑、页面与组件、存储与迁移、种子与 mock、测试代码 |

执行计划、现状分析、路线图属过程文件，不作为被审对象；它们与上述对象冲突时，作为一致性审计的发现报出。

### 6.2 路由：对象 × 问题

| 要回答的问题 | 适用对象 | 用什么 |
| --- | --- | --- |
| 这份需求文档本身写得好不好 | 需求文档 | `check-prd` |
| 这份数据模型本身好不好 | 数据模型 | `domain-modeling` 的质量自检清单，由独立审计者执行 |
| **两个对象是否一致** | 验收标准 ↔ PRD/覆盖清单/测试；任意两类之间：规则 ↔ 代码全部路径、需求 ↔ 模型 ↔ 目录 ↔ 源材料、测试规格 ↔ 规则、图示 ↔ 模型、目录 ↔ 其代码镜像 | `consistency-audit` |
| 这段代码本身有没有缺陷 | 代码 | 作者侧代码缺陷自查（见第 2 节矩阵），不属审计、不出报告 |
| 运行中的流程对不对 | 原型 | `journey-audit` |

- **Task 收尾审计含两类以上被审对象时，使用一致性审计。** 已查实的漏审集中在对象之间：文档写明的规则，代码只在部分路径执行；图上的计数落后于模型；验收条款与裁定冲突。单个对象内部的质量检查抓不到这一类。
- **代码实施批**：作者完成代码缺陷自查并修复后，才算修复批次完成；M2 独立审计 = 一致性审计（规则 → 代码全部路径）。
- **文档任务**：按涉及对象与问题选择收尾审计 skill；不同保存或修复分组不产生额外审计触发。
- `consistency-audit` 未安装时，派发方在 prompt 里写明三项要求：Oracle 逐条拆分并逐条给出判定；判"缺失"必须附检索记录（模式、路径、结果）；代码侧列出能改变该状态的全部入口并逐一核对。

### 6.3 审计动作与风险触发

Task 的全部改动完成、作者侧验证通过后，执行一次独立审计，覆盖整个 Task，并对登记表全部未关闭条目给出核销或明确的继续登记理由。深度按 6.5 的 materiality 选择，标准按 6.2 的对象与问题选择。代码或文档的改动量、保存次数不构成触发器。

| 动作 | 触发 | 检查范围 | 执行者 |
| --- | --- | --- | --- |
| **独立审计（initial audit）** | Task 整体完成且作者侧验证通过 | 整个 Task 的适用标准、相关相邻契约，以及登记表全部未关闭条目的状态 | fresh auditor；不得是作者 |
| **定向复核（focused recheck）** | P0/P1 在本 Task 内修复完成，且未改变契约、模型或范围 | 只核这几条 P0/P1 及其影响路径/邻接回归，一次即止 | 同一审计者；不得参与修复 |
| **完整重审（full re-audit）** | 修复改变了契约、模型或范围，原结论依据不再成立 | 重新执行受影响 Task 的全部适用标准与未关闭条目核销 | fresh auditor；不继承作者或上一轮结论上下文 |

审计者参与修复后即失去该产物后续审计资格。**Fresh auditor** 是没有参与生成或修复、没有继承前轮结论上下文的新执行实例；底层模型相同也必须从当前产物与 Oracle 建立判断。

P2/P3 不形成固定第二轮审计；低成本问题作者侧修复，其余记录给下一个 Task。没有独立核销的作者侧修复保持该状态，不与独立确认混同。审计次数不设默认预算，也不能把“没有预算”理解为每次保存或每批修复都全量重审。

### 6.4 作者侧修复覆盖与完成边界

作者负责 Task 过程中的测试、变异检查、回放、doc-sync 和代码缺陷自查。发现按风险自动分流：P0/P1 在本 Task 内修；P2/P3 能低成本处理的直接修，其余留在登记表。需要业务判断的歧义或取舍按批提交用户；无需为常规修复、审计或规定的复核另请求许可。

每项修复在作者侧验证记录中列明下表。记录放在宿主的过程文档中，不写入 PRD、spec 或 skill 正文的变更说明。

| 字段 | 核对要求 |
| --- | --- |
| 规则与问题 | Oracle 条目、原偏差与目标行为；修复不能自行降低判据 |
| 受影响载体 | 同一口径涉及的全部文件、段落、模板、通用 Prompt、镜像和构建产物；同根因的其他可达入口 |
| 已处理与证据 | 实际 diff、检索结果、脚本差集、测试/回放或变异结果；不以“已经改了”替代证据 |
| 未处理边界 | 尚未覆盖或无法核验的位置、原因与后续 owner；不能把部分覆盖写成全部完成 |
| 确认状态 | 作者侧已修、待独立核销，或独立确认已修；标明判断所依据的证据 |

完整批次结束前，作者核对所有受影响载体及相邻回归，相关分发产物同批重建。P0/P1 完成后进入 6.3 的一次定向复核；仅作者侧完成的 P2/P3 保留“作者侧已修，待后续审计确认”，由后续 Task 收尾审计核销。

比当前集成基线更差的回归必须在整合前修好，用作者侧回放与测试证明，不另开审计。修复未改变契约、模型或范围时，不因 diff 大或 materiality 标签单独重复全量审计。

Before any commit, push, PR or merge action, obtain the authorization required by the host's Git workflow. Audit routing does not grant delivery authorization.

### 6.5 Materiality 与审计深度

**M0 机械维护**：不改变业务或技术语义的文字、格式、路径、链接、索引及证据归档。由作者做针对性机械验证，不因该改动新增独立复审。证据维护时记录当前权威报告/产物 hash、diff 摘要和命令结果，保留在宿主过程记录中。

**M1 局部语义变化**：局部枚举、异常分支、文案语义或明确的 local change target，未改变上位范围、ownership 或跨模块骨架。收尾审计核对这些目标、所有相关执行路径与相邻回归；M1 本身不触发每批修复后的复审。

**M2 重大变化**：范围、拆分、业务目标、验收出口；实体、关系、状态机、金额/计算/时间口径；权限与数据范围；ownership、跨模块 contract、幂等、回调、补偿；核心旅程或架构主干。Task 收尾按全量深度审计；修复使契约、模型或范围改变时，原 Oracle 下的结论不能沿用，按 6.3 做 fresh 完整重审。

无法确定时按 M1 评估，命中 M2 条件则升级深度。“编辑很机械”不能替代风险判断。涉及对外发布内容的任务（例如脱敏后公开），首次审计按全量深度执行，同样遵守一次收尾审计及必要 P0/P1 复核。

**外部 Oracle 变化**：先做影响分析。无影响时保留判断证据；局部影响核对对应路径；契约、模型或范围变化时更新冷启动输入并重新建立完整结论。远程更新本身不等于需要审计，不能用旧报告证明新 Oracle 已满足。

每次自行进入审计、修复或复核，向用户说明动作、依据、实际结果和后续处置。一次定向复核的限制不等于作者只允许修复一次；未确认的偏差必须继续如实登记，不能为了结束任务宣告已通过。

### 6.6 回收：handoff 契约

审计者交回的内容按下列字段组织：

| 字段 | 要求 |
| --- | --- |
| `status` | `continue` / `complete` / `blocked` |
| `summary` | 非空 |
| `evidence` | 可指到文件、行、用例编号 |
| `next steps` | 下一步由谁做什么 |
| `blocker` | `status` 为 `blocked` 时必填 |

1. **无效、缺失或超长的交回直接判失败**，不截断、不当作正常结束。
2. **终态措辞写明"这是执行者报告的结果，不是独立认证"。**
3. **报告文件是权威，handoff 只是补充**；结论不得只存在于 handoff 中。
4. **P0/P1 发现须经独立反驳**：主 Agent 另起一个实例，只给它该条发现与证据，要求尝试推翻；推不翻的才作为成立转呈，推翻了的连同反驳理由一并转呈用户。其余级别标"未经反驳"。反驳结论记在登记表该条的"反驳"一栏（未推翻 / 推翻，附"部分已写明"一类说明）；反驳原文与审计原文一样是临时的。

### 6.7 遗留登记与核销范围

- 未关闭问题统一保存在模块登记表。Task 收尾审计携带全部未关闭条目，逐条写明已修、部分修、未修或不再适用及证据；不为旧项另开审计，也不能只选择容易核销的条目。
- P0/P1 定向复核只检查规定的高风险修复及影响路径；其余作者侧状态、延后理由和未核对边界保留在登记表，给后续 Task 使用。
- 仅作者侧修复未获独立确认时，不从正文删除。连续跨 Task 未处理的条目提示其风险与继续延期原因，不设默认三轮预算或机械地追加全量审计。

### 6.8 登记与清理（主 Agent 执行）

审计者只写本轮原文。**主 Agent 回收后，在同一轮内完成下列步骤；完成前本轮审计不算结束。**

1. **转呈**：把审计原文原样转呈用户；P0/P1 完成独立反驳（6.6）。
2. **登记**：更新模块登记表（6.10）——新发现逐条写入；已有条目按核销表更新状态；**经独立审计或规定复核确认已修的条目从正文删去，只在更新记录留一行；仅作者侧修复的条目保留待后续审计确认**；涉及用户裁定的，裁定进决策档案。
3. **原文先入库，再删除**：本轮原文（审计报告、反驳记录）随本轮工作提交一次，取得提交 hash；登记表每条的"来源"写这个 hash 与原文路径；随后删除原文。原文留在版本历史里，按"来源"可随时取回。**未入库就删除的原文无法取回，不得这样做。**
4. **改写入链**：删除前检索全部指向原文的链接——项目状态、执行计划这类长期过程文档改为指向登记表；决策档案需要保留证据时写"来源提交 + 原文路径"，不写相对链接；结果文件（需求文档、模型、规范、测试用例规格）不链接任何过程记录，有则直接删去链接，只有删后句子读不通时才改写该句本身。**不为保留审计内容而修改任何结果文件。** 删除后验证无断链。
5. 登记与清理属 M0 证据维护，不触发新一轮独立审计，也不表示任何产物或审计结论获得通过。

### 6.9 原文的写法与中断接手

- **原文存在期间只追加**：同一轮原文若分多次写入，后写入的执行者只追加自己的顶层章节，不修改既有章节。原文在删除前一字不改。
- **中断后接手的报告要标证据等级**：新执行者据前一执行者录制产物重建的判定属二手证据，须逐条标注，并在报告开头声明两类条目的数量。

### 6.10 过程记录的存放

审计报告、复审报告、反驳记录、走查报告、测试执行报告都是**过程记录**：记录工作怎么做成。需求文档、数据模型、规范、测试用例规格与覆盖清单是**结果文件**：项目交付的东西。两类不混放。

- **按模块存放**：每个模块在需要时建自己的过程记录目录，位置由宿主契约的 `host.processRecordsDir` 声明（相对模块目录的子路径，见 `process/kit-architecture.md` 第 9 节），与该模块的结果文件分开存放；未声明时请用户指明。不把所有模块的过程记录集中到一个大目录，方便按模块查看与管理。
- **常驻的只有两类**：
  - **未关闭问题登记表**，每模块一份：`<module>_open_findings.md`。用户只读这一份就知道该模块还剩什么问题
  - **测试执行报告与走查报告**，每模块各一份，覆盖或追加更新，不按日期另开新文件
- **临时的**：本轮审计原文与反驳记录，按 6.8 登记并入库后删除。图示校验、探针日志、脚本差集这类工具输出不单独落文件，命令与结论写进原文的附录。

**登记表的格式**（模板见 `templates/tob_open_findings_register.md`）：

- **按业务子域分节**；每节内分三段：**待修复**、**待用户裁定**、**延后事项**。修法唯一、不需要业务判断的归待修复；规定本身缺失或有歧义、需要用户拍板的归待裁定；已知未做且不是缺陷的（缺业务输入、尚未接通）归延后事项
- **待修复**用表格，每条一行：编号、问题、位置、级别、复现或判据、反驳
- **待用户裁定**每条一个小节：现状、缺什么、后果（有则写）、需要裁定什么、推荐方案、理由、位置、反驳
- 每条末尾增加空白的 **用户裁定** 栏，由用户填写；问题关闭时随该条一并删除，裁定按 6.8 进入决策档案
- **位置写成可点击的链接**，指向具体行（`文件#L行号`，相对登记表所在目录）；行号以登记时的版本为准
- **写到用户不回看原文就能判断**：问题写现象与后果，不写审计术语；复现写可操作的步骤或可检索的判据
- 表头注明版本、更新日期与各段条数；表尾注明来源——哪几轮审计、随哪个提交入库
- **版本管理**：登记表每次改动都随工作提交入库，版本号加一。表尾的**更新记录**每个版本一行：版本、日期、新增哪些编号、删去哪些编号及原因（已修 / 已裁定 / 不再适用）、依据（复核提交或决策档案）。编号只增不复用，删去的编号在更新记录里仍可查到；条目的完整历史内容按依据提交从版本历史取回
