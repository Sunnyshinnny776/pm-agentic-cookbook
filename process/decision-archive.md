# 决策档案机制

> 本文档定义**决策档案**这套机制：它记什么、目录与格式长什么样、什么该入档什么不该、以及它与其他文档的边界。
>
> 它是方法论层的规范，与任何具体项目无关。宿主项目在自己决策档案目录的 `README.md` 里声明本项目的用法——载体清单、并发写入的拓扑、机检脚本名。

---

## 0. 它解决什么问题

项目通常有三类文档：需求文档记「是什么」，规则文档记「怎么做」，状态文档记「做到哪了」。**没有一类记「为什么是这样，以及不是哪样」。**

这个缺口在人独自工作时不明显——决策者有连续记忆，理由在脑子里。但在 AI 协作里它立刻致命，因为存在一个结构性不对称：**决策者有连续记忆，执行者每次会话都失忆。** 而所有既有文档记的都是决策的**结果**，没有一处记决策的**边界**：当时摆在桌上还有哪几个选项、为什么被杀掉。

于是一个判断力正常的失忆执行者，读到结论后会独立推导出那些当初被否决的方案，然后当作新想法提出来。这不是模型犯蠢，是信息缺失下的理性行为。

档案补的就是这个信息。它带来三件事：

1. **裁定的前提变得可证伪。** 一条裁定压在若干前提上；前提写下来，它就从不透明的事实变成可检验的结构。前提到期或被推翻时，能精确地"保留裁定、收窄依据"，而不是发现规则还在、理由是假的、且没人知道它曾经有过理由。
2. **「当初就选错了」成为一句说得出口的话。** 出问题时第一个问题永远是：选错了还是做砸了？只有结论没有备选时，**唯一可见的东西是执行**，所有失败都会归因到执行上——设计层面的错误因此永远不可见，然后穿过一次又一次执行反复重演。
3. **规则可以被安全地改。** 规则文档说「要做 X」，不说代价。不知道代价，后来者要么不敢动，要么随手就动。

还有一半价值在**写的时候**，不在读的时候：一个说不出自己否决了什么的结论，不算想清楚了，只是一次碰巧落对的偏好。强制写出备选，这个动作本身把直觉转成知识，并照出那些根本没有第二个选项的"假决策"。

## 1. 目录结构

```
decisions/
  README.md              ← 宿主项目的用法说明
  proposed/<class>/      ← 已提出，尚未裁定，或已裁定但落地物尚不存在
  implemented/<class>/   ← 裁定生效且落地物已存在（可指到文件 / commit）
  rejected/<class>/      ← 经裁定否决
```

lifecycle 目录之间只能**向前流转**：`proposed` → `implemented` 或 `proposed` → `rejected`。用 `git mv` 移动，保留历史。

**`implemented` 的判据是落地物已存在、可指到文件或 commit。** 已裁定但未落地的留在 `proposed/`，并在 `## Acceptance criteria` 写明转档条件。这样 `Status` 与目录一致才是硬判据，机检守护的才不是一个软约定。

### class 闭集

| class | 覆盖 |
| --- | --- |
| `domain` | 领域模型 / 业务口径裁定 |
| `product` | 需求文档的功能范围、流程、状态机取舍 |
| `spec` | 界面、组件、交互的可复用规则决策 |
| `process` | 协作方式、门禁、方法论 |
| `kit` | 方法论工具包自身的架构决策 |

**闭集不得随意新增。** 一份决策落在哪一类，看**它约束谁**：约束业务对象 → `domain`；约束某个模块的功能范围 → `product`；约束所有页面的做法 → `spec`；约束人与 AI 怎么协作 → `process`；约束工具包自身 → `kit`。

宿主项目若确需增删 class，改本文档的闭集定义并同步机检脚本，不在单个项目里私自扩展。

### 文件名

`yyyy-mm-dd-topic-title.md`，日期是该裁定**首次做出**的日期，不是建档日。历史裁定补录时从会话记录、版本历史或相关文档的裁定记录表推定；推定不出时用文件创建日并在正文标注。

## 2. 文件格式

前三行固定，供机检：

```markdown
# Decision: <标题>

Status: implemented
```

`Status` 三种取值，且**必须与所在 lifecycle 目录一致**：

| 取值 | 目录 |
| --- | --- |
| `Status: proposed` | `proposed/` |
| `Status: implemented` | `implemented/` |
| `Status: rejected — <一行原因>` | `rejected/` |

第 3 行之后可跟一个可选元信息块，每行一个 `Key: value`，允许的键：`Date`、`Deciders`、`Supersedes`、`Superseded-by`、`Related`。

### 正文骨架

| lifecycle | 必需章节 |
| --- | --- |
| `proposed/` | `## Problem` → `## Proposal` → `## Alternatives considered` → `## Acceptance criteria` → `## Risks` |
| `implemented/` | `## Problem` → `## Decision` → `## Alternatives considered` → `## Consequences` |
| `rejected/` | 保留提案期章节，裁定理由写在 `Status:` 行 |

「→」表示推荐顺序；门禁只查章节齐全，不查顺序。章节标题按整行匹配，`### Problem`、`## Problems` 都不算。

---

## 3. 三条纪律

1. **`## Alternatives considered` 每篇必填。** 只写真实存在过的备选与真实的否决理由，**禁止编造**。这一节是本机制的核心价值——它是对治"反复重开已决问题"的那一条，其余格式规则都是为它服务的。历史裁定补录时若无法重建当时的备选，写下这行标记，不要编：

   ```markdown
   <!-- decision-format: alternatives-not-recorded (retrofit) -->
   ```

2. **档案永不改写成相反的决策。** 结论变了就新建一篇 supersede 旧篇，两篇用 `Supersedes:` / `Superseded-by:` 互相链接。被 supersede 的旧篇留在原地，不删。允许的原地修改只有：补充证据指针、修正笔误、流转 lifecycle。

3. **跨档案引用用相对 markdown 链接**，不用裸编号。链接可机检、可随文件移动修复，编号不能。

## 4. 入档判据

### 两条判据，满足**任意一条**即入档

1. **跨越了这份文档的边界** —— 这条裁定会约束别的模块、别的会话、或别的执行者。只约束本节本文档的取舍留在原地。
2. **能写出真实的被否决项** —— `## Alternatives considered` 填得出来，且不用编。

**判据是「或」不是「且」**：一条裁定只要跨了边界就值得留档，哪怕当时只有一个可行方案；反过来，一条只影响本文档的取舍，如果它是在几个真实方案之间挣扎过的，那份挣扎也值得留下。

### 判据 1 单独成立时，追问一句

判据 1 会吸纳一批其实只是**规则**的条目——它们跨边界，却从未发生过选择。典型是「所有页面必须复用标准组件」：它约束全部页面，但「各自造轮子」从来不是被认真考虑过的方案，只是没有规则时的默认状态。照直入档会产出一篇 `Alternatives` 写着「无真实备选」的薄档案，而内容已经在它的 owning spec 里。

所以**判据 2 不成立、仅判据 1 成立时，追问：当时是否真的发生过一次选择？**

| 情形 | 处置 |
| --- | --- |
| **发生过选择**，哪怕最终只有一个可行方案（某个约束排除了其余） | **入档**。`Alternatives considered` 如实写清是什么约束排除了其余 |
| **没发生过选择**——只是把「没有规则时的默认状态」写成了规则 | **不入档**，归其 owning spec |

**兜底**：判为「规则」之后，若它没有 owning spec，**去建 spec，不得拿档案顶替**。否则这道追问会变成一个丢东西的口子——判成规则、又无处安放、最后哪儿都没有。

判据 2 成立时不触发这道追问：写得出真实的被否决项，本身就证明发生过选择。

**不要用「规则本体是否已有 owning spec」代替这道追问。** 它是代理指标，会误杀合规约束、外部系统能力边界、源材料硬性规定这一类——它们常常只有一条路，规则本体也一定住在某个 spec 里，却恰恰最该留档：后来者会问「为什么非得这样」，答案是「因为某个约束」，而**约束会过期**，过期后规则就该重审。

### 只满足判据 1 时，Alternatives 怎么写

如实写**为什么没有备选**——是约束只允许一条路、是时间窗口只够做一件事、还是当时没人想到别的。这是关于决策空间的真实陈述，不是编造。

```markdown
## Alternatives considered

无真实备选。<约束> 使得只有这一条路可走：<说明>。
```

**禁止**为了凑满这一节而虚构从未被认真考虑过的方案——那比空着更坏，它让读者以为这个决策经过了实际上没发生过的比较。

### 四个边界情形

| 情形 | 处理 | 理由 |
| --- | --- | --- |
| **明确决定不做某事**（放弃、暂缓、划为边界） | **必须入档，优先级最高** | 备选就是"做"，否决理由通常是成本或冲突——这是真实备选。而且这类最容易被后来的会话重开 |
| **待决项 / 开放议题** | **一律不入档** | 它们是"还没裁定"。档案记的是已做出的选择，把待决项放进来是污染 |
| **纯格式、命名、排版取舍** | 不入档 | 归规则文档或代码注释 |
| **推翻或修订既有裁定** | **必须入档** | supersede 链要求两端都在档案里，否则链断 |

### 判不准时的默认值

**默认不入档，但必须记进当前任务的裁定记录表。**

两边的代价不对称：漏一条的损失是"它还在表里，将来可以补建"；错进一条的损失是"多一篇 Alternatives 敷衍的档案"，而敷衍的档案会稀释整个档案的可信度——读者一旦发现有几篇是凑数的，就不再相信其余的。

## 5. 三步顺序：判据筛 → 查重扫 → 写

**判据和查重是两道独立的关，缺一不可，且有先后。** 判据回答"这条值不值得留档"，查重回答"这条是不是已经有人留过了"。

只跑判据会产出冗余档案——一条裁定完全可能判据全绿、却是另一条已入档裁定的直接推论。而冗余档案对档案可信度的伤害，与敷衍档案相同。

### 建档前查重

档案由多方写入，且写入方可能同时在跑，所以建档前必须查重：

1. **扫一遍目标 class 目录**（三个 lifecycle 下的同名 class 都要看），按 topic slug 判断这条裁定是否已经有人建过。日期不同不代表是两条——同一裁定被两个会话分别补录时，日期推定结果可能不一致。
2. **已存在**：不新建。要补充的证据指针、链接、后续影响，就地改那一篇。
3. **发现重复两篇**：保留信息更完整的一篇（通常是 `## Alternatives considered` 写得更实的那篇），把另一篇的独有内容合并进去，然后删除多余的那篇——版本历史保留了它。**这不是 supersede**，supersede 用于结论改变，重复只是同一条裁定的两个副本。
4. **命中查重（是既有裁定的推论）**：在父裁定的档案里补一节吸收它（原议题 + 关闭结论各一句），不另建文件。
5. **两篇结论实质冲突**：说明它们其实不是同一条裁定，或者存在未收敛的分歧。**停下来交决策者裁定**，不要自行合并。

唯一残留的碰撞面是同日同 slug 的文件名重复，由上面的查重步骤覆盖。

## 6. 两段式工作流

| 阶段 | 载体 | 成本 | 时机 |
| --- | --- | --- | --- |
| **捕获** | 当前任务的裁定记录表 | 一行，极低 | 裁定发生**当场** |
| **留档** | 决策档案 | 一篇，需要写 Alternatives | 任务收尾时，按判据筛 |

表是捕获网，档案是耐久记录。**任务收尾必须核一遍表**——逐条判定入档或不入档，不留悬空。这一步不做，表里的条目会随任务文档一起沉底。

## 7. 审议过程与规范结果：只有前者进档案

一条裁定会产生两样东西，**只有第一样是过程性的**：

| | 例 | 归属 |
| --- | --- | --- |
| **审议过程** | "曾议是否给某角色补授某权限；结论不补授" | **只进决策档案** |
| **规范结果落到文档上的那个值** | 权限矩阵里该格的"无此权限" | **留在需求文档 / 规则文档** |

判据一句话：**删掉这一行，实现者会不会做错？**

- 删掉"某议题曾被提出并否决" → 实现者不受影响 → 只进档案
- 删掉矩阵里那个取值 → 实现者不知道该不该给这个权限 → 必须留

一个"否定取值"看起来像否定结果，但它是**规范性陈述**（这个角色没有这个权限），可实现、可测试。它与"我们否决了一个提案"不是一回事。

**被否决的方案不是项目内容，不写进需求文档。** 闭合的裁定项不在需求文档里保留专门的「已裁定项 / 已关闭项」表格——那是审议记录。三层分工：

| 层 | 记什么 | 载体 |
| --- | --- | --- |
| 发生了什么 | 「本版关闭了某议题，见档案」 | 需求文档的变更记录，一行 |
| 是什么 | 规范取值、范围边界结论 | 需求文档正文与矩阵 |
| 为什么、放弃了什么 | 议题、备选、否决理由 | 决策档案 |

**一条例外**：当实现与规范**有意不一致**且这个偏离是被登记的，该登记**留在需求文档正文**。它不是审议记录，是一条读者必须在规范旁边当场看到的警告——否则会照规范去实现或写测试，把有意为之的偏离当成缺陷。

范围边界同理：「本模块不含某能力」这类结论在需求文档留一行加链接，否则每个读者都要重新问一遍这是遗漏还是有意不做。理由与备选仍进档案。

### 过程性编号不写进结果性文档

同一条分界也管编号。审计发现号、走查观察号、待办清单项号、任务计划的裁定项号——这些编号定义在**过程性文档**里，而过程性文档在任务结束后会被清理。结果性文档长期存在，编号于是悬空：读者读到它，在任何现存文档里都查不到它指什么。

判据：**这个编号在本文档内能否被解释？不能的话，读者要去哪里查？那个地方会不会消失？**

| 编号来自 | 处理 |
| --- | --- |
| 过程性文档（会被清理） | **改成实质描述**。替换通常增加信息而非减少 |
| 结果性文档（长期存在） | 可用，但带可理解名称而非裸编码 |

**变更记录是重灾区**：它天然记录"这一版因为什么改了什么"，而"因为什么"常常是一个过程性编号。变更记录的职责是让读者知道这一版改了什么，用读者查不到的编号写就没尽到职责。

**存量靠遇到即修**：编辑某一节时若该节有悬空编号，在同一次变更里改掉。不排全文档批量清理——两类编号长得一样，只有看定义位置才能分，批量替换必然误伤。

## 8. 保持 implemented 档案与实现同步

`implemented/` 的档案描述的是**已经发生的现实**，所以它必须随现实更新：代码或文档改了路径、改了文件名、改了某个默认值或字段名之后，在同一次变更里把档案里对应的事实改掉。

**只改事实，不改决策。** 路径、名称、结构属于事实；`## Decision` 里的裁定本身、`## Alternatives considered` 里的备选与否决理由，一律不动（要改结论就 supersede，见纪律 2）。

不做这件事的后果是档案慢慢和现实脱节，最后变成没人敢信的历史文件——那时它既不能阻止重开，也不能作为证据，只剩维护成本。

## 9. 怎么找一条裁定

按成本从低到高，三条路径：

1. **看目录树**。`lifecycle/class/` 两级已经把范围切得很细，加上文件名自带日期与 topic，多数情况下列一下目标目录就够了。
2. **一条命令的全量总览**：

   ```bash
   grep -rn --include='*.md' '^# Decision: ' <decisions 目录>/
   ```

   输出是「路径 + 标题」的一行一条清单，lifecycle 与 class 直接体现在路径里。要连状态一起看就把模式换成 `'^# Decision: \|^Status: '`。
3. **按内容搜**。找"这个话题裁定过没有"时直接搜关键词，命中后再打开正文。

**正文按需读**：清单与标题是便宜的，正文是贵的。判断相关性用前两条，确认细节才打开文件。

### 为什么不设索引文件

**故意不设 `INDEX.md`**，三条理由都与"怕冲突"无关：

1. **索引是派生数据。** 它要展示的信息——lifecycle、class、日期、标题——已经完整编码在每个文件的路径和首行里。把派生数据提交进仓库，等于给同一份事实建立第二个副本，而两个副本迟早会不一致。
2. **它给每个提交制造无关噪音。** 任何一次新增、改名、流转 lifecycle 都会改到这个全局文件，于是每次变更的 diff 里都躺着一个和本次改动无关的条目变化，评审要在噪音里找信号。
3. **它要养一套工具。** 生成器、渲染、新鲜度校验，全是为一条已经被目录树和搜索覆盖的发现路径付的维护成本。

同构机制在数百篇规模上仍判定目录树加仓库搜索足够，并曾把已有的生成式索引移除——"靠重新生成解决冲突"这条退路也被否决过，因为重新生成让冲突解决变机械，但阻止不了无关变更修改同一产物，也消不掉评审噪音。

**不要为了"方便浏览"加索引。** 需要总览时用上面那条命令，它零维护、零漂移、零噪音。

## 10. 与其他文档的边界

**档案是裁定的唯一权威。** 一条裁定的完整叙述（Problem / Decision / Alternatives / Consequences）只写在这里一次；其余载体保留一行摘要加一条链接，不重复理由与备选。两处叙述冲突时以档案为准。

理由：同一条裁定的完整版本存在两份，就有两份会漂移。

| 载体 | 它承载什么 | 裁定在它里面的形态 |
| --- | --- | --- |
| **需求文档** | 功能需求、业务规则本体 | 写"规则是什么"；为什么选这条、放弃了哪条，链接到档案 |
| **领域模型的裁定节** | 数据模型语境下的结论 | **保留结论与它在模型里的位置**（读的人需要就地看懂），删掉重复的理由与备选叙述，加链接 |
| **规则文档 / 规范** | 可复用规则 | 规则本体留在最小 owning spec，决策与备选进档案 |
| **状态文档** | 进度、活跃分支、已完成清单 | 一行摘要 + 链接 |
| **任务文档的裁定记录表** | 该任务范围内的裁定索引 | **捕获网**，见第 6 节。够格的转档案后保留一行 + 链接 |
| **待决表 / 开放议题表** | **尚未裁定**的开放项 | 与档案无关。裁定做出后从待决表移除，按判据决定是否入档 |
| **变更记录表** | 版本流水 | 只记"哪一版改了什么"，不承载裁定理由 |
| **会话记忆 / 私有笔记** | 个人偏好、环境事实、跨会话待办 | **项目级裁定一律不放这里**——它对协作方与评审不可见，也不随版本库演进 |

**存量迁移不做批量搬迁**：既有载体里已写下的裁定，遇到时按需转档（改动那份文档的人顺手做），或按计划分批处理。

## 11. 机检与它的边界

可机判的部分应由脚本守护：首三行格式、`Status` 与 lifecycle 目录一致、class 属闭集、按 lifecycle 校验必需章节齐全、`## Alternatives considered` 非空（去掉首尾空白后少于 20 个字符即视为空，挡住「无」「略」这类占位；retrofit 标记视为合规）、文件名模式、相对链接可解析，以及**拒绝目录下出现 `INDEX.md`**。

**两条永远无法机检**，只能靠评审：

- **档案与实现是否同步**（第 8 节）
- **备选是否真实**（纪律 1）——机器分不出"如实记录的备选"与"为了填满而虚构的备选"，而这恰恰是整套机制的价值所在

还有一条比机检更根本的缺口：**没有任何机制能强制触发建档**。"这一轮有没有发生裁定"是关于对话的事实，不是关于变更内容的事实，扫描变更的脚本判不出来。可行的缓解是把提问放到必经路径上——交付说明里必填一行"本次记录了哪些裁定，或为何没有"，以及在会话收尾处提问。这些不构成强制，只是把沉默变成明示主张。

## 12. 宿主项目要自己声明的部分

本文档不覆盖以下内容，宿主项目在自己决策档案目录的 `README.md` 里写：

- 本项目有哪些裁定载体（具体的需求文档、领域模型、状态文档、任务计划路径）
- 谁在往档案里写、在哪个分支写（并发写入的拓扑）
- 机检脚本的实际名称与接入方式
- 本项目的具体举例

## 来源

本机制的目录与格式借鉴了一个公开的开源 Agent Note 体系的约定，并针对本方法论的场景做了加固——入档判据、判据与查重的两道关、审议过程与规范结果的分离、过程性编号规则为本文档新增。它同时属于 ADR（Architecture Decision Record）这一成熟模式家族，差异在于面向的读者是**每次会话都失忆的执行者**，而非有连续记忆的人。
