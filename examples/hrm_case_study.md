## 一、起点：先定阶段门禁

### 遇到的问题
早期让 AI 连续完成建模、写需求文档、生成页面。上游一处理解偏差，会沿着数据模型、需求文档、原型和测试一路放大；AI 也容易把自己的自审结果当成用户验收。

### 怎么做
- 每个阶段结束先由 AI 自审，再交用户审查；用户明确确认后才进入下一阶段。AI 如实给出成熟度、缺口和证据，不自行宣告通过。
- 数据模型先于需求文档。需求文档底层的逻辑缺失或有误时，先改模型再改文档；底层数据缺失时停下交用户决定，不砍掉中间层做降级实现。

### 结果
阶段门禁写进了 [流程概览](../process/overview.md)，成为后续所有改进的前提：每次回改都能定位到出错的那一阶段，而不是在原型上打补丁。

## 二、规则从返工里长出来

### 遇到的问题
走查时发现的交互问题，修完一处，换个页面又会重犯。原因是结论只停留在那次修复里，没有写进任何下次会被读到的地方。

### 怎么做
- 每次实现后回问「这次有没有可复用、已确定的规则」，有就写进最小的 owning spec；写法是通用规则在前、项目示例可拆分，换项目只换示例。
- 规则是否成立由用户裁定，AI 只提出候选。一次阶段收尾时，从三批修复与两轮走查中沉淀出十余条规则，分别进入 UI/UX、集成、工程规范和对应的 skill。

### 结果
[参考规则库](../specs/README.md) 中的大量条款都来自这类返工。一条规则从走查返工到写进 spec 的完整过程，见 [规则沉淀示例](sample-spec-capture.md)。

## 三、审计体系的四次调整

审计体系不是一开始就设计好的，而是在暴露问题后逐步调整出来的。

| 暴露的问题 | 调整 |
|------|------|
| 同一个 Agent 生成产物又自己审计，带着生成时的上下文与结论，难以发现自身遗漏 | **作者与审计者隔离**：作者是 Agent 时，审计与旅程走查交给独立的子代理冷启动执行，主 Agent 提供完整输入并原样转交结论 |
| 回头盘点漏审问题，发现大多落在对象之间：规则写在需求文档里、执行在代码里，各自审都没问题；有一个最严重的问题跨过了四轮审计 | **按「被审对象 × 要回答的问题」选审计方式**：需求文档审计只回答「文档写得好不好」，涉及两类以上对象时做一致性审计，逐条核对规则与代码的全部执行路径 |
| 一次审计批次在模块目录里新增十几个报告文件，用户要知道「现在还剩什么」得打开好几份 | **每个模块一份常驻的问题登记表**：只列未关闭的问题，修复确认后移出正文；审计原文入库一次后删除，需要时从版本历史取回 |
| 每个修复批次后都派一轮全量审计，默认预算 3 轮成了默认次数，审计与等待裁定占去大部分周期 | **每个任务收尾只做一次独立审计**：P0、P1 当场修复并由同一审计者复核，P2、P3 能顺手修的修掉，其余带到下一个任务 |

### 一条反复出现的教训
需求文档的变更记录里常混进审计发现号、走查观察号这类过程性编号。这些编号的定义所在的报告会在任务结束后清理，编号就悬空了。这个问题修过一次又复发——当时清理了正文，规则却没写下来。之后定下「过程性编号不写进结果性文档」并写进规范，才不再复发。**只修现象不写规则，问题会回来。**

## 四、权限体系重建（进行中）

### 遇到的问题
早期每个模块按角色硬编码菜单和权限判断。随着岗位、组织层级、委托与附加授权进入需求，各模块对「谁能做什么」的理解开始漂移，同一档治理权限在不同层级上被重复定义成不同角色。

### 怎么做
- 先统一模型再动代码：用户通过岗位获得角色授权，角色与组织无关，岗位是角色在具体组织上的实例；功能权限与数据范围分开表达。
- 建一份系统级角色权限登记表，作为角色全集、权限点目录与全局规则的唯一出处；模块需求文档只写本模块的授权决定，不重述标准。
- 按「数据模型 → 需求文档 → 分批落码」推进，每批收尾做一次独立的一致性审计。

### 现状
权限内核、统一求值与命令层已经落码并经过多轮独立审计；页面运行时仍走旧的判断方式，切换在后续任务中进行。这部分尚未完成，本文不把它当作已验证的结果。

## 五、把反复叮嘱的规则交给门禁

### 遇到的问题
有些写作规则靠反复提醒也守不住，例如不在文档里用章节号符、译本要随原文同步、skill 不得引用宿主私有路径。每次靠审计发现，成本都落在下游。

### 怎么做
- 能机判的规则做成门禁，由 `doc-sync` 一次跑完：skill 目录与 frontmatter、自包含、通用层领域名词、宿主私有路径、决策档案格式、章节号符、译本同步、安装包成员一致性等。
- 用 hooks 在编辑后自动跑相关门禁，在收尾时跑全部门禁并提醒沉淀规则；hooks 只提醒，不阻止操作。

### 结果
门禁与 hooks 随 cookbook 发布，见 `tools/gates/` 与 `tools/hooks/`。门禁只检查格式与结构，业务是否正确仍要人判断。

## 局限与未做的事

- 原型用于确认需求、承接研发讨论，不是生产代码；能否复用由研发结合项目判断。
- 业务准确性始终依赖懂业务的人确认，AI 审计只提供重新核对的机会。
