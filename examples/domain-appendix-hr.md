# 领域 Provider 示例：连锁零售的人事需求

领域 Provider 为通用 skill 补充业务语义。本文以虚构的连锁零售企业为例，说明如何整理 HR 领域的术语、核对项和验收场景。

## 先划清三层职责

| 层 | 负责的内容 | 例子 |
| --- | --- | --- |
| Service Definition | 通用执行顺序、输入与输出、停止条件 | 如何逐项核对、怎样报告缺口 |
| Service Provider | 显式选择的领域知识及检查映射 | 员工与任职的区别，组织数据范围要核对什么 |
| Consumer | 当前项目的已确认事实与调用参数 | 要审的文档、领域名、组织结构、规则版本 |

结构约定见 [Kit 架构](../process/kit-architecture.md)。Provider 的字段和文件结构服从消费它的 Definition；不同 skill 的 Provider 接口可以不同。

## 写 Provider 之前需要确认什么

- 领域名及适用边界：是 HR 通用语义，还是某个宿主自己的约定。
- 对象及关系：分别描述员工、任职、组织、角色，明确每个标识符回答哪个业务问题。
- 时间语义：有效日期、事件时间、空结束日期的含义由哪份已确认文档规定。
- 核对依据：领域常识提示应该问什么，宿主确认的 Domain Model、PRD 和验收标准决定本次应该是什么。
- 消费接口：Definition 接收哪些补充项，如何引用它们，如何说明未加载 Provider。

不要把具体公司的组织层数、角色矩阵、金额、人员数量或内部状态当成领域的普遍规则。某项规则只在一个宿主成立时，让宿主的来源文档持有它。

## 示例一：术语表

虚构组织为集团总部、东区/西区及门店。组织管理员和组织协管员是示例角色；具体授予哪些动作，由宿主确认。

| 术语 | 要区分的问题 | 调用时需要的宿主依据 |
| --- | --- | --- |
| 员工 | 自然人与任职记录是否被混用 | 对象定义、标识符及关系 |
| 任职 | 一次任职归属哪个组织、在哪段时间有效 | 有效期和组织归属规则 |
| 组织 | 业务归属与当前页面所在位置是否被混用 | 组织模型及数据范围 |
| 角色 | 身份、动作权限和数据范围是否分开 | 已确认的权限矩阵 |

这张表给出提问方向。它不指定员工能否同时有多条任职，也不替宿主决定组织层数或跨组织权限。

## 示例二：领域核对项

| 示例编号 | 核对问题 | 需要定位的证据 | 可派生的场景 |
| --- | --- | --- | --- |
| HR-DEMO-1 | 员工标识与任职标识是否各有明确含义 | Domain Model 的对象定义与关系 | 同一员工的两条示例任职能否被正确区分 |
| HR-DEMO-2 | 任职有效日期在相邻环节是否采用同一口径 | 已确认的日期字段及边界规则 | 生效日、结束日、空结束日的边界 |
| HR-DEMO-3 | 动作权限与组织数据范围是否都受检查 | 权限矩阵、动作契约、范围规则 | 同角色访问东区一店与西区一店的数据 |
| HR-DEMO-4 | 外部人员数据重复到达时如何识别同一业务事实 | 已确认的同步标识、版本及冲突规则 | 重复消息、旧版本消息、缺少关联对象 |

编号在本例内定义。正式 Provider 按消费方 Definition 的约定使用稳定编号，让报告中的编号能回到该 Provider 的定义。

核对项应说明要找什么证据，不能仅凭出现了某个字段就判断能力已实现。材料没有规定预期行为时，保留问题交用户确认，不把示例填成真实项目的答案。

## 接口与目录的组织方式

下面是接口位置的示意，具体文件名由 Definition 的契约决定：

```text
skills/<skill>/
  SKILL.md
  references/
    providers/
      <domain>/
        <Definition 要求的领域文件>
```

调用方应明确说按哪个领域执行。业务话题本身不能代替领域参数。执行者记录实际是否加载了 Provider；指定领域没有可用 Provider 时，按 Definition 的缺失处理规则报告，不编造专项检查。

Provider 单独附加到 skill 时，先核对它与当前 Definition 的接口是否相容。术语和规则有所变化后，核对所有消费该项知识的输出模板、检查映射和场景，避免只改名词而保留旧预期。

## 怎样检查一个 Provider 是否可用

1. 对同一份合成需求分别执行显式指定领域和未指定领域的调用，保持其他输入一致。
2. 分开观察通用核对与领域补充，记录实际加载的文件和输出中的声明。
3. 检查每条领域发现能否定位到输入事实、领域核对项及宿主 Oracle。
4. 由独立执行者核对实际产物与预先固定的判据；作者说明用于解释边界，不能代替证据。
5. 由用户判断领域知识及业务预期是否正确。一次合成用例的结果只覆盖该次可见行为。
