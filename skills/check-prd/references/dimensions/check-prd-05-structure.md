# 文档结构完整性检查

> Supporting reference for the `check-prd` skill. 在执行文档结构完整性检查时加载；单独使用时请先提供待检查的 PRD 内容。

## 维度说明

PRD文档的结构完整性直接影响评审效率和开发交付质量。一份结构清晰、章节完整的PRD能降低沟通成本、减少需求遗漏。《决胜B端PRD模板v2.0》提供了标准化的PRD文档结构，共包含14个章节。

**核心理论框架：**

1. **PRD标准文档结构**（《决胜B端PRD模板v2.0》）：项目背景 → 需求基本情况 → 商业分析 → 项目收益目标 → 项目方案概述 → 项目范围 → 项目风险 → 术语和缩略语 → 参考文献 → 功能需求（含产品框架概述、需求详解、异常处理） → 数据埋点 → 角色和权限 → 运营计划 → 待决事项。

2. **文档版本管理**（《决胜B端PRD模板v2.0》）：PRD交付前必须标记版本号；需求范围、业务规则或产品语义发生变化时，严格记录变更时间、原因、修改人、审核人。纯展示层维护不单独占用 PRD 业务版本号。

3. **功能描述五种规则类型**（《决胜B端PRD模板v2.0》10.2节）：事实、约束、触发条件、推论、计算——功能规则描述必须归类到这五种类型之一，确保无遗漏。

4. **自顶向下的设计思路**（《决胜B端》第2章）：B端产品总体建设遵循"从抽象到具体"的原则，PRD文档结构应体现这一思路。

5. **Overview PRD 的上位约束职责**：当文档是 PRD 包中的 Overview 时，它不替代 Sub PRD 的页面详细设计，而是定义产品/模块定位、范围边界、信息架构、跨模块数据流、全局状态/权限/安全/异常基线、子文档拆分和后续详细设计约束。

## 检查清单

### 5.1 文档元信息

- [ ] **文档头部信息完整性**
  - 检查内容：PRD是否包含审核人、重要性、紧迫性、需求方、编写人、提交日期等元信息
  - 优质标准：所有字段已填写，审核人和需求方明确到具体人名，日期格式统一
  - 问题标志：元信息缺失或填写不完整（如审核人写"待定"）
  - 参考依据：《决胜B端PRD模板v2.0》文档头部格式

- [ ] **版本变更记录**
  - 检查内容：是否维护了完整的PRD版本变更记录
  - 优质标准：需求范围、业务规则、字段、状态、流程语义、权限、异常处理、验收口径或待决事项变化时，完整记录变更时间、变更内容、变更提出部门与理由、修改人、审核人、版本号；版本号递增合理
  - 豁免边界：仅修复 SVG 连线锚点与排版、表格视觉样式或不影响信息含义的文档格式，且正文内容与产品语义均未变化时，不要求新增修改记录或递增版本号
  - 问题标志：无版本记录；产品语义变化后未更新版本号；或变更记录不完整。不得仅因纯展示层维护未新增版本而判为问题
  - 参考依据：PRD 版本记录服务于业务内容的评审与追溯；展示层维护由 Git 或资产历史追溯，避免制造无业务含义的版本噪音

- [ ] **无自我宣告通过的语言**
  - 检查内容：PRD 是否在修改记录"理由"列、待决事项结论或自检结论处，出现替用户下达"通过/成功"结论的自我背书
  - 优质标准：可保留客观自评（成熟度评分、待完善项、AI 自审结果），但通过与否的裁定权留给用户；审查动作如实表述（如"AI 参考 check-prd skill 进行 N 维度自审"）
  - 问题标志：出现"PRD 成熟度满足评审要求""数量合理""通过 N 维度终审/封板"等表述；或审核人仍为"待定"却已宣告通过
  - 参考依据：AI 自评与用户裁定的职责边界

### 5.2 前置章节完整性（第1-9节）

- [ ] **项目背景（第1节）**
  - 检查内容：是否有详细的项目背景描述
  - 优质标准：包含业务现状、面临问题、解决思路，有数据支持
  - 问题标志：背景空泛或缺失
  - 参考依据：PRD模板第1节——"不论是多简单的需求，都会有需求背景"

- [ ] **需求基本情况（第2节）**
  - 检查内容：是否包含需求提出人、功能使用人、受影响人、场景、发生频率、核心痛点、需求价值
  - 优质标准：七个字段全部填写，场景用六要素描述（人物、时间、地点、起因、经过、结果）
  - 问题标志：多个字段缺失，或场景描述过于简略
  - 参考依据：PRD模板第2节需求基本情况

- [ ] **商业分析（第3节）**
  - 检查内容：是否包含目标市场与客户分析、竞品分析两大板块
  - 优质标准：目标市场分析包含目标市场、市场规模、市场特征、发展趋势、客户画像、客户痛点、卖点提炼；竞品分析包含商业模式、目标客户、运营推广策略、市场份额、产品分析、核心价值
  - 问题标志：商业分析章节缺失或仅有空壳
  - 参考依据：PRD模板第3节商业分析表格

- [ ] **项目收益目标（第4节）**
  - 检查内容：是否有量化的、符合SMART原则的项目目标
  - 优质标准：目标具体可衡量，包含验收标准和成功标准，有收益预期
  - 问题标志：目标模糊或缺失
  - 参考依据：PRD模板第4节

- [ ] **项目方案概述（第5节）**
  - 检查内容：是否用简要语言概述了核心功能或项目方案
  - 优质标准：列举了所有核心功能feature，或概述了产品方案、运营方案、技术方案
  - 问题标志：无概述直接进入细节
  - 参考依据：PRD模板第5节

- [ ] **项目范围（第6节）**
  - 检查内容：是否明确了项目涉及的系统、产品、接口和影响范围
  - 优质标准：列出所有相关系统和责任方，标注影响范围，确保无遗漏
  - 问题标志：范围不明确，后续开发时才发现遗漏的关联方
  - 参考依据：PRD模板第6节——"梳理项目范围，提前确认项目关联方、影响方"

- [ ] **项目风险（第7节）**
  - 检查内容：是否识别并记录了假设、约束和各类风险
  - 优质标准：列出产品风险、运营风险、技术风险，每个风险都有应对方案
  - 问题标志：无风险分析，或只列风险不提应对方案
  - 参考依据：PRD模板第7节

- [ ] **术语和引用文档（第8-9节）**
  - 检查内容：是否解释了文档中的专业术语和缩略语，是否列出了参考文档
  - 优质标准：所有首次出现的术语有定义；引用的外部文档有明确链接
  - 问题标志：文档中充满缩略语但无解释，或引用了但找不到参考文档
  - 参考依据：PRD模板第8-9节——"尽量不要自己定义缩略语"

- [ ] **引用可理解性与可追溯性**
  - 检查内容：扫描业务规则编号、缺口编号、审计问题编号、规则块字母、节点/文档/段落缩写，以及“见某文档第 X 节”一类引用；逐项判断读者能否在当前位置理解并直接定位来源
  - 优质标准：正文优先写完整业务含义；已完整陈述的规则不再追加冗余编码；必要的跨文档引用使用“描述性名称 + 可跳转 Markdown 链接”，首次出现时解释编码；局部编号与完整描述同处定义
  - 问题标志：只写 `BR-009`、`G-B`、规则块字母或标题缩写；引用外部文档只有编号而无链接；同一文档堆叠多套代码体系但没有索引或定义；编码删除后不影响语义却仍反复出现
  - 审查动作：先全量检索候选编码，再区分“冗余编码，删除”与“必要追溯，补名称/出处/链接”，报告中列出具体位置和建议改写
  - 参考依据：PRD 面向跨角色评审者，正文需独立可读；引用承担追溯职责时必须可定位

### 5.3 功能需求章节（第10节）

- [ ] **产品框架概述（10.1节）**
  - 检查内容：是否包含系统框架图、数据模型图、业务流程图、状态机图中的至少2-3种
  - 优质标准：四种图都有提供，框架图层次清晰，数据模型用ER图表达，流程图用跨部门泳道图表达
  - 问题标志：无任何框架概述图，直接进入页面级描述
  - 参考依据：PRD模板10.1节——"系统框架图、数据模型图、业务流程图、状态机图"

- [ ] **功能清单表格（10.1.2节）**
  - 检查内容：是否提供了子系统、页面、多端覆盖情况的功能清单
  - 优质标准：功能清单以表格形式呈现，包含子系统名称、页面名称、各端支持情况（PC/H5/App等），一目了然
  - 问题标志：无功能清单，或功能列举散落在文档各处
  - 参考依据：PRD模板10.1.2节功能清单表格格式

- [ ] **需求详解的规范性（10.2节）**
  - 检查内容：功能需求描述是否采用结构化方式（查询条件、列表字段、规则描述）
  - 优质标准：
    - 列表页有查询条件表格（字段名称、默认值、字段类型、备注）
    - 列表页有列表字段表格（字段名称、默认值、字段类型、开放修改、必输项、备注）
    - 规则描述按五种类型归类：事实、约束、触发条件、推论、计算
    - 每个功能模块有业务流程图和页面交互说明
  - 问题标志：功能描述为大段自然语言叙述，无结构化表格和分类
  - 参考依据：PRD模板10.2节的结构化描述格式和五种规则类型

- [ ] **生成模板结构符合性**（与 create-prd 模板对齐）
  - 检查内容：第 10 章章节结构是否符合生成模板的固定结构——10.1 产品框架概述应为固定五节（10.1.1 应用架构图 / 10.1.2 数据模型引用或局部数据模型 / 10.1.3 业务流程图 / 10.1.4 状态机图 / 10.1.5 功能清单），10.2 按功能模块展开，10.3 异常处理方案
  - 优质标准：正文章节编号只承载模板规定的内容；工作方法产物（如「页面 × 规则块」覆盖矩阵、自检清单）只出现在附录/自检区，不占用正文编号；Sub PRD 对上位文档的引用带可跳转的 markdown 锚点链接
  - 问题标志：PRD 发明模板外章节占用 10.1.x 编号；把审计产物或工作方法写入正文结构；引用上位文档只有"见 Overview 第 X 节"字样而无链接
  - 参考依据：create-prd 第 10 章生成指引的固定模板结构；结构违规导致 PRD 包内文档形态不一致，本检查项发现默认不低于 P1

- [ ] **Overview PRD 专项结构**（仅 Overview PRD 必查）
  - 检查内容：如果 PRD 是 Overview，是否完成上位结构设计，而不是停留在目录级摘要。
  - 优质标准：
    - 明确产品/模块定位、目标用户、业务价值、In Scope / Out of Scope。
    - 明确 PRD 包或子文档拆分矩阵，说明每个子文档覆盖对象、依赖关系、优先级、边界。
    - 提供信息架构、核心业务流程、跨模块数据流、关键状态机或状态基线。
    - 引用已有 Domain Model 或说明核心实体读写边界，不越界重建下游模块实体。
    - 定义全局权限、审计、安全、异常、埋点和验收基线，约束后续 Sub PRD。
    - 明确哪些页面级字段、交互、按钮、弹窗、异常和验收将在 Sub PRD 中展开。
  - 问题标志：只列子模块名称但无拆分边界；没有跨模块数据流；没有全局非目标；没有说明 Sub PRD 后续需要补什么；把 Overview 写成单个页面详细 PRD。
  - 参考依据：PRD 包拆分与自顶向下设计原则。

- [ ] **异常处理方案（10.3节）**
  - 检查内容：是否有专门的异常情况处理方案章节
  - 优质标准：覆盖断网、断电、误操作、数据丢失、并发冲突等异常场景，每种异常有处理方案
  - 问题标志：无异常处理章节，或仅提"参见后续补充"
  - 参考依据：PRD模板10.3节

### 5.4 后置章节完整性（第11-14节）

- [ ] **数据埋点（第11节）**
  - 检查内容：是否按公司统一标准描述了需要监控的按钮、页面、事件
  - 优质标准：埋点设计覆盖核心操作路径，标注了事件名称、触发条件、采集参数
  - 问题标志：无埋点设计，或只有"后续补充"的占位符
  - 参考依据：PRD模板第11节

- [ ] **角色和权限（第12节）— 角色权限定义表**
  - 检查内容：是否以**角色权限定义表**的形式逐个权限点声明授予结论，且该表可被权限管理模块机读、可作为实现层权限矩阵的预言
  - 优质标准：列结构为 `序号 / 菜单栏导航 / 页面导航 / 权限点编码 / 敏感 / 全部角色列 / 范围收窄`；权限点编码为三段式 `模块:对象:动作` 且全系统唯一；一个可点击的操作一行；格子只有 `✓`/`○`/`—`/`*` 四种取值
  - 问题标志（逐条核）：
    - 权限描述模糊（如"管理员有所有权限"），或未精确到页面元素级别
    - **角色列不齐**——省略某个角色会使「无权限」与「未评估」不可区分，读者无法判断是评估后认定无权限还是压根没考虑
    - **格子里写了数据范围**（"✓（本级）""✓（辖区）"）——数据范围是角色属性，全系统配置一次，不该逐格重复
    - **本章重复罗列角色定义**——项目已有统一角色来源时，角色是什么由那一处说，本章只说各角色在本模块拿到什么
    - **敏感字段或导出随数据范围一并授予**——二者应独立授权，前者驱动留痕，后者附二次确认
    - 仅当 PRD 涉及多组织（集团、上下级组织）时适用：**上级角色持有跨组织的操作类或审核类权限**——审核通常是组织内部动作，跨组织的把关走另一个节点；若确需上卷，PRD 必须给出依据
    - 仅当 PRD 涉及多组织时适用：全局配置类动作（全局字典、模板、任务下发）被当作组织数据求值——它们不属于任何单一组织，不该叠加组织范围判定
    - **本章保留了「已裁定项 / 已关闭项」表格**——那是审议记录，归决策档案；PRD 只留规范取值（矩阵里那个 `—` 是规范性陈述，必须留）、变更记录里一行"本版关闭了什么"，以及实现与规范**有意不一致**时的偏离登记（读规范的人必须当场看到，否则会把有意为之的偏离当成缺陷）。判据：删掉这一行，实现者会不会做错
  - 参考依据：PRD模板第12节；本 skill「角色权限定义表」格式标准

- [ ] **运营计划（第13节）**
  - 检查内容：是否说明了需要建立的运营流程、推广计划、部署计划
  - 优质标准：列出新建运营流程、客服处理流程、推广计划、部署方案
  - 问题标志：完全没有运营视角的考量
  - 参考依据：PRD模板第13节

- [ ] **待决事项（第14节）**
  - 检查内容：是否明确列出了文档中结论待定的事项
  - 优质标准：待决事项有编号、描述、负责人、预计决策时间，且数量不应过多（过多说明PRD成熟度不够）
  - 问题标志：明显有未决事项但未记录，或待决事项数量超过10项
  - 参考依据：PRD模板第14节

## 常见问题诊断

| 问题现象 | 根本原因 | 改进方向 |
|---------|---------|---------|
| PRD只有功能描述，缺少背景和分析 | 把PRD当功能说明书写 | 按14节标准结构补充前9节 |
| 功能描述是大段文字 | 不熟悉结构化描述方法 | 采用表格+规则分类的标准格式 |
| Overview PRD 只有目录索引 | 误把 Overview 当目录页 | 补充定位、范围、信息架构、跨模块边界、全局状态/权限/异常基线和 Sub PRD 约束 |
| 无版本记录，或产品语义变化后未登记 | 缺乏文档管理意识 | 建立版本管理规范，对业务内容变化逐次记录；纯展示层维护不单独升级版本 |
| 权限描述模糊 | 未做角色权限定义表 | 按格式建立「权限点编码为主键、角色列齐全」的定义表 |
