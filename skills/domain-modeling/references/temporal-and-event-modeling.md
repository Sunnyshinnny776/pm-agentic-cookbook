# 时态事实、集合载体与事件投递建模

## 1. 办理对象与生效事实分层

审批单、申请单、调整单等办理对象负责记录意图、审批过程、材料和来源；真正被下游读取的业务事实应由独立的生效实体承载。

- 办理状态不能直接替代事实有效性。
- 下游计算只读取覆盖目标日期的生效事实。
- 为保证历史可复现，下游快照冻结命中的事实记录 ID、关键值与内容 hash。
- 办理对象只用于来源追溯，不作为事实缺失时的静默回退源。

## 2. 时间区间粒度服从不变量

先写出区间不重叠不变量，再决定实体粒度。例如不变量是“业务对象 × 项目 × 日期区间”，生效段就必须落到对象与项目粒度；包含多个项目的办理主单不能只维护一组共享结束日期。

时态实体至少定义：

- 生效开始与结束边界是否包含端点；
- 开区间如何表达；
- 正常追加、未来生效、历史插入和归档如何处理；
- 数据库排斥/唯一约束；
- 任一分段失败时的事务回滚边界。

### 唯一关系解析与闭区间交接

- 业务声明“来源对象 + 时间坐标唯一确定目标记录”时，解析结果必须 exactly one。零条表示必要事实缺失，多条表示唯一性被破坏；两者都必须阻断，禁止让用户临时挑选、回退默认记录或静默过滤。
- 闭区间相邻交接必须定义确定性端点算法。若新区间从 `new_start` 生效，旧区间应结束于 `new_start` 前一个最小时间单位（日期粒度即 `old_end = new_start - 1 day`），禁止同一端点同时属于新旧区间。
- 区间不重叠不能只依赖应用层先查后写。应使用数据库排斥约束，或在同一事务内使用等价的串行化/锁定守卫；并发冲突只允许一笔提交，其余事务整体回滚并返回冲突对象与区间。

### 命令时再校验与原子快照

- 页面预览、用户工作上下文和先前查询结果都不是写命令的可信事实。创建历史业务对象时，服务端必须在同一事务内重读权限、状态、唯一关系和当前有效配置。
- 事务应原子冻结命中的事实 IDs、创建时状态、配置版本、内容 hash 与成员快照。任一校验或快照写入失败时主对象零落库，禁止产生半完成业务对象。
- 创建完成后，可变工作上下文和主数据后续变化不得改写既有业务快照；需要更新时生成明确的新版本、重算轮次或替代对象。

## 3. 条件集合必须有权威载体

当某个状态要求配置一组子项时，不能只在 UI 多选值或临时 JSON 中表达。

- 建立拥有来源、有效期、状态和审计字段的集合关系实体。
- 状态进入该分支时校验集合非空和成员有效性。
- 状态离开该分支时原子截断或失效当前集合。
- 下游快照冻结成员 ID 集合及 hash，后续主数据变化不改写既有快照。

## 4. 历史重分段使用 immutable audit

会改写历史时间轴的创建、截断、重分段和归档操作必须生成 append-only 证据：

- 重分段事务 ID；
- 操作类型；
- before/after snapshot；
- 来源办理对象或明细；
- 内容 hash；
- 操作人、system actor 与时间。

业务变更和成功日志在同一事务提交。若事务失败且新事实从未落库，失败审计使用 planned business key，事实外键允许为空，禁止创建悬空引用。

## 5. 一对多事件使用投递账本

一个上游事件需要作用于多个下游对象时，首次接收事件就冻结目标集合，并为每个目标建立 delivery record。

- 幂等键至少包含 `event_id + target_id`。
- 每个目标保存 PENDING/APPLIED/FAILED/SKIPPED、重试次数、最后错误和完成时间。
- 自动补偿只重试 FAILED 目标，已成功目标不得重复产生副作用。
- 全部目标进入完成态后，上游事件才标记完成。
- 后续新增目标不自动补消费历史事件；确需补发时生成明确的新事件或补偿任务。

## 6. 业务事务使用 transactional outbox

业务事实变更需要可靠通知下游时，业务事实、执行凭证与 Outbox 必须在同一数据库事务提交，避免“业务已成功但事件漏发”或“事件已发但业务回滚”。

- 先定义聚合粒度：一条业务对象版本对应一条事件，或一条执行凭证对应一条事件；不得在重试时临时改变粒度。
- `event_id` 必须由稳定业务幂等身份确定性派生；重复执行返回既有业务结果与 Outbox，不新建事件。
- Outbox 冻结事件类型、业务版本、执行凭证 IDs/hash、规范化 payload hash 与发布状态。
- publisher 只重试 Outbox 投递，不重新执行业务事务；每次尝试 append-only 保存结果、错误类别、时间与 worker。
- 临时 transport/timeout 故障可重试；不可重试错误或耗尽进入可见 FAILED，告警责任人。人工 replay 复用同一 `event_id` 并追加尝试证据。
- consumer 使用 `event_id` 或独立 receipt 唯一键幂等；重复消费返回既有结果且零副作用。consumer 失败不得回滚已经提交的 producer 业务事实。
- poison event 必须保留可查询的失败状态、脱敏错误和同 ID replay 入口，禁止通过生成新 ID 绕过去重与审计链。

## 7. 自检清单

- [ ] 办理对象与生效事实是否分层？
- [ ] 时间段粒度是否与不重叠不变量一致？
- [ ] 声明唯一确定的关系是否对零条与多条都显式阻断？
- [ ] 闭区间交接是否定义端点算法并具备数据库并发守卫？
- [ ] 下游是否冻结事实 ID 与 hash？
- [ ] 创建命令是否在事务内再校验，并保证校验/快照失败时主对象零落库？
- [ ] 条件集合是否有持久化关系实体和有效期？
- [ ] 历史重分段是否有 append-only 前后值证据？
- [ ] 未落库事实的失败审计是否避免悬空外键？
- [ ] fan-out 是否冻结目标集合并支持逐目标重试？
- [ ] 业务事实、执行凭证与 Outbox 是否在同一事务提交？
- [ ] event ID 是否稳定，publisher retry 是否避免重做业务事务？
- [ ] consumer 是否有 receipt/唯一键幂等，poison event 是否可见并以同 ID replay？
