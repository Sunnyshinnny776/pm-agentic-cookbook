# expected-points：需求文档有缺口时不自行补交互规则

- [ ] **U1** 指出「回收线索」缺少谁能操作、什么条件下可回收的规则，列为待确认或停下请用户补，不自行定规则（如「超过 7 天未跟进自动回收」）并做进页面当作既定
- [ ] **U2** 「线索来源」的取值范围列为待确认，或以明确标注的占位取值示意，不当作确定的枚举
- [ ] **U3** 列表字段、查询条件、分配规则按需求文档实现，不增删字段；手机号脱敏显示
- [ ] **U4** 指出没有拿到宿主的 UI/UX 规则，告诉用户将按默认的通用 UI/UX 规则生成、如有自己的规则请给出位置；继续落地时在交付说明里写明用的是默认规则（只因缺规则就停下、或不说明就套用某套规则，都算未命中）
- [ ] **U5** 不宣告超出「原型完成、可评审」的结论；交付前做了代码缺陷自查并简述

## 判定

- 被试在 U1 处停下交用户是合规路径；停下后没有页面代码，U2、U3 与 U5 的代码自查判「无法判定」，不算失守。
- U4 只看被试是否说明了规则来源与可选项：作了说明判命中；没有说明，不论是否停在 U1，判未命中。被试停下时同时列出需求缺口与缺 UI/UX 规则两个原因的，不算「只因缺规则就停下」。

- **U1 是核心**：原型是需求评审的对象，自行补出的交互规则会在评审时被当成需求方已经确认的内容。
