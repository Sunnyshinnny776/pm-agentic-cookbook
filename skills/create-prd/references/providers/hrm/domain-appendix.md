# HR 系统领域 PRD 适配

> 当业务领域属于 HR 系统、HRM、HCM、薪酬、组织人事、考勤、绩效、社保公积金、个税、招聘、员工服务或人力预算时加载本文件。

## 适用范围

本附录用于增强通用 B 端 PRD，不限定产品形态。HR 系统既可能是商业化 SaaS，也可能是企业自研系统、私有化交付项目或客户二开项目。PRD 生成时应同时保留产品形态差异和 HR 业务域约束。

## HR 领域产品定型补充

在原有“商业属性 × 功能类型”之外，补充识别以下信息：

| 维度 | 可选值 | 说明 |
| --- | --- | --- |
| HR 子域 | 组织人事 / 薪酬 / 算薪 / 个税 / 社保公积金 / 考勤 / 绩效 / 预算 / 审批 / 员工服务 / 数据分析 | 决定术语、角色、状态、数据敏感性和上下游模块 |
| 文档粒度 | 系统级 / 模块级 / 子功能级 / 迭代级 | 功能模块级和子功能级 PRD 必须更强调页面、字段、规则、异常和验收 |
| 交付形态 | SaaS / 自研 / 私有化 / 二开 | 影响多租户、配置化、权限边界、实施交付和运营章节 |
| 管控模式 | 集团管控 / 分级授权 / 单组织使用 / 多租户隔离 | 影响组织树、数据权限、审批流和配置继承 |

## 前置材料读取规则

生成 HR 领域 PRD 前，应优先读取已有项目材料，并以已有材料为事实来源：

| 材料类型 | 用途 |
| --- | --- |
| 解决方案或源材料 | 确认业务目标、原始规则、上下游边界 |
| Domain Model / 数据模型 | 确认实体、字段、关系、状态、级联、审计字段 |
| 已有模块 PRD | 确认相邻模块的术语、入口、状态、数据流和权限 |
| 角色权限文档 | 确认角色、组织数据范围、按钮级权限 |
| UI/UX 规范或原型 | 确认页面结构、交互模式和设计约束 |
| 接口或集成文档 | 确认外部系统、同步方式、幂等、失败重试 |

如果现有材料与用户新需求冲突，PRD 中必须标注冲突点和待确认项，不得直接改写既有业务口径。

## PRD 包拆分规则

复杂 HR 模块不强制写成单个大 PRD。满足任一条件时，应优先输出 PRD 包：

- 二级菜单超过 3 个。
- 涉及 3 个以上外部或相邻模块。
- 有多个状态机或多个锁定/审核/归档状态。
- 包含批量导入、同步、审批、计算、异常处理中的 2 类以上复杂流程。
- 单个第 10 章预计会超过全文 50%。

PRD 包建议结构：

| 文档类型 | 内容范围 |
| --- | --- |
| Overview PRD | 模块目标、角色、信息架构、全局流程、状态机、跨模块数据流、子 PRD 清单 |
| Sub PRD | 单个二级菜单或子功能的入口条件、页面交互、字段、规则、异常、权限、验收标准 |
| Audit Report | 后续由 check-prd 输出的问题清单和修正建议 |

## HR 领域功能模块 PRD 必填项

每个 HR 功能模块或子功能 PRD 必须覆盖以下内容：

| 项目 | 说明 |
| --- | --- |
| 入口与前置条件 | 从哪个菜单、页面、状态或外部事件进入；依赖哪些基础配置 |
| 适用对象与时间口径 | 员工、岗位、组织、薪资档案、薪资期间、考勤周期、预算周期等 |
| 读取实体 | 本功能只读引用哪些主数据或相邻模块数据 |
| 写入实体 | 本功能创建、更新、锁定或归档哪些实体 |
| 状态机 | 涉及草稿、待提交、审批中、已生效、已锁定、已归档等状态时必须写 |
| 权限与数据范围 | 角色权限、组织树范围、本人/本部门/下级组织/全集团范围 |
| 审计与追溯 | 操作人、操作时间、变更前后值、来源文件、审批记录、异常处理记录 |
| 异常与补偿 | 数据缺失、重复、冲突、权限不足、外部同步失败、并发编辑、锁定态修改 |
| 幂等与版本 | 导入、同步、批量生成、审批回写、计算重跑必须说明幂等策略 |
| 验收标准 | 正常流、异常流、权限流、锁定态、重试/重导/重算场景 |

## HR 领域常见实体检查

根据具体子域选择适用实体，不要求全部出现：

| 子域 | 常见实体 |
| --- | --- |
| 组织人事 | Employee、Organization、Department、Position、PositionAssignment、EmploymentStatus |
| 薪酬/算薪 | SalaryProfile、SalaryItem、PayrollRule、PayrollPeriod、PayrollBatch、PayrollResult |
| 定调薪 | SalaryAdjustment、SalaryGrade、SalaryGradeStandard、ApprovalRecord |
| 考勤 | AttendancePeriod、AttendanceRecord、LeaveRecord、OvertimeRecord |
| 社保公积金 | SocialSecurityAccount、HousingFundAccount、ContributionBase、ContributionRecord |
| 个税 | TaxProfile、TaxRateTable、TaxAccumulator、SpecialDeduction |
| 人力成本预算 | CostBudget、BudgetLine、BudgetPeriod、BudgetVersion |
| 审批 | ApprovalInstance、ApprovalNode、ApprovalAction、ApprovalCallback |

功能模块级 PRD 中如需使用已有 Domain Model，应以“本功能涉及实体表”替代完整重建 ER；只有缺少数据模型时才从业务描述中补建局部模型。

## HR 领域业务规则检查

PRD 生成时必须检查以下高频风险：

| 风险 | 检查方式 |
| --- | --- |
| 组织数据越权 | 是否明确组织树、责任范围、平级隔离、上看下规则 |
| 员工多任职/多档案 | 是否区分员工、岗位分配、薪资档案等不同粒度 |
| 时间口径混乱 | 是否区分自然月、薪资月、考勤周期、社保月、预算月、税款所属期 |
| 状态锁定冲突 | 审批中、已锁定、已归档、已发放等状态是否禁止修改 |
| 导入覆盖历史 | 重导、同步、批量生成是否保留版本和明细，不覆盖历史证据 |
| 外部系统失败 | OA、考勤、社保、税务、财务等接口失败是否有重试和人工处理入口 |
| 敏感数据暴露 | 薪资、证件号、银行卡、个税等是否要求脱敏、加密或权限控制 |
| 规则配置继承 | 集团配置、组织配置、本地扩展之间是否有覆盖和锁定规则 |

## HR 领域验收标准模板

每个子功能至少输出以下验收场景：

| 类型 | 验收场景 |
| --- | --- |
| 正常流 | 给定合法角色、合法数据和开放状态，操作完成后实体、状态、审计记录正确 |
| 异常流 | 给定缺失、重复、冲突或非法数据，系统阻断或提示，并生成可追溯异常 |
| 权限流 | 给定无权限角色或越权组织数据，页面、按钮、数据均不可见或不可操作 |
| 锁定态 | 给定业务对象已审批、已锁定或已归档，修改入口被禁用或要求解锁流程 |
| 幂等流 | 重复导入、重复同步、重复提交或重复回调不产生重复业务结果 |

## HR 领域角色与权限适配

### 角色分层提示

按子域选择适用角色，不要机械全部套用：

| 角色类型 | 典型角色 | 权限关注点 |
| --- | --- | --- |
| 平台/集团管理 | 平台管理员、集团 HR 管理员、集团组织管理员 | 全局字典与标准配置、跨组织查询、授权下发；**这些动作多为 `GLOBAL` 范围维度** |
| 业务域条线 | SSC（共享服务）、COE（专家中心）、HRBP（业务伙伴）负责人 | 各自业务域的集团级配置与管控；三支柱是**业务域划分**，不是组织层级 |
| 区域/事业部 | 事业部 HR 负责人、区域人力总监 | 辖区监管、催办、汇总上报；**跨组织不代办操作类** |
| 组织执行 | 分子公司 HR、薪酬专员、考勤管理员、社保专员 | 本组织数据维护、导入、同步、异常处理 |
| 审核审批 | 薪酬经理、部门负责人、财务 BP | 组织**内部**审核、驳回、确认；只读查看敏感明细 |
| 员工自助 | 员工、主管 | 本人数据、团队摘要、申请与确认 |
| 系统集成 | OA 回调账号、接口服务账号 | API 权限、最小化授权、审计追踪 |

**命名纪律**：管理员类角色统一以「管理员」结尾，「经理」「专员」留给岗位。角色（权限主体类，组织无关）与岗位（角色在具体组织上的实例）必须分层，避免「分公司管理员」这类把组织层级写进角色名的命名——它会让同一档治理权限在不同层级上重复造角色。

### HR 数据范围档

HR 系统必须额外说明这些范围之间的差异，并区分**查看档**与**操作档**：

| 档位 | 含义 |
| --- | --- |
| 全集团 | 全部组织节点 |
| 自定义组织集 | 按业务条线分管的若干组织，与树形档**不可比**（可能比"本级"宽，也可能只含一个组织） |
| 本级及以下 | 本组织节点 + 其全部子节点 |
| 本级 | 仅本组织节点 |
| 仅本人 | 员工自助场景 |
| 租户范围 | 多租户 SaaS |

对上层角色，**查看档与操作档通常不同**：看得到辖区/全集团，只能操作本级。

### HR 敏感数据基线

薪资金额、个税、证件号、银行卡、社保公积金基数、绩效结果、背调与健康信息一律标 `敏感 = 是`，并落实：

- **查看**：默认脱敏，敏感字段查看须**独立授权**，不随组织范围继承
- **导出**：与查看**分离授权**，附二次确认、水印/加密、操作人与行数留痕
- **委托授权**：授予敏感权限时事由必填，授权有有效期
- **审计**：敏感字段的查看与解密动作留痕（临时查看类可按项目裁定豁免，须显式登记）

### HR 常见的审核与审批区分

HR 系统里「审核」与「审批」常被混用，写进权限表前必须分清：

| | 发生位置 | 参与方 | 权限承载 |
| --- | --- | --- | --- |
| **内部审核** | 组织/部门内部 | 薪酬经理、部门负责人 | 系统内权限点，`OPERATE` 类，**不跨组织上卷** |
| **审批** | 跨层级或外部流程 | 组织决策层、集团高管、OA | 常由外部流程承接，系统内可能**没有独立权限点** |

若某个模块的跨组织把关走的是 OA，则权限表里不应出现"上级角色审核下级组织数据"的格子——那件事不在系统内发生。

## 领域专项自检表

归位自通用层的自检附录。**生成 PRD 后的自检环节，在通用自检之外追加本表。**

当业务领域为 HR 系统时，额外检查以下项目：

| 检查项 | 检查内容 | 状态 |
| --- | --- | --- |
| HR-01 组织数据权限 | 是否明确组织树、责任范围、平级隔离、集团/租户边界 | ✅已覆盖 / ⚠️需完善 / 不适用 |
| HR-02 人员粒度 | 是否区分员工、任职、岗位分配、薪资档案、账号等不同粒度 | |
| HR-03 时间口径 | 是否区分自然月、薪资月、考勤周期、社保月、预算月、税款所属期等 | |
| HR-04 敏感数据 | 薪资、个税、证件号、银行卡、绩效等是否有脱敏、加密、导出限制 | |
| HR-05 状态锁定 | 审批中、已生效、已锁定、已归档、已发放等状态是否禁止非法修改 | |
| HR-06 导入同步 | 批量导入、外部同步、审批回写是否有版本、明细、幂等和失败处理 | |
| HR-07 跨模块数据流 | 是否与组织、人事、考勤、薪酬、预算、OA、财务等上下游一致 | |
| HR-08 审计追溯 | 是否保留操作人、时间、来源、前后值、文件、审批和异常记录 | |
| HR-09 验收场景 | 是否覆盖正常、异常、权限、锁定、幂等场景 | |

## 领域识别关键词

通用层的产品定型表只保留「有 Provider 的垂直领域」这一格，识别关键词由各 Provider 自己声明。本领域的关键词：

HRM、HCM、人事、组织、薪酬、算薪、考勤、绩效、社保、公积金、个税、预算、员工服务。

命中任一即按本附录适配，强化组织权限、敏感数据、时间口径、状态锁定、导入同步、跨模块数据流。

## 敏感字段清单

通用层第 12 章只给类别（个人身份证件、金融账户、报酬与评价结果、健康与背景信息），具体字段由本节给出：

薪资、个税、证件号、银行卡、社保、公积金、绩效结果、健康与背调信息。命中即标敏感，驱动三件事：委托授权时事由必填、查看留痕、导出二次确认。

## 输出边界

PRD 正文应聚焦产品需求、业务规则、交互设计、数据边界和验收标准。没有业务依据的外部行业规则或法律细节应标注为待确认，不得直接写成确定性需求。
