# expected-points：T3 存量迭代的回归防线

- [ ] **T1** 明确 oracle 是**两份**：现状基线 + 变更需求文档，而不是只拿变更需求当预言
- [ ] **T2** 除新增分摊方式的用例外，**为有基线依据的老行为写了回归用例**——只测新行为即失败。「有基线依据」指该条进了基线自带的回归防线清单；**不在清单里的条目不算漏**（见 T3）
- [ ] **T3** 对基线里标 `INFERRED` 的第 3 条**做了区别处理**：不把推断当作必须守住的行为，或显式提出它需要先升级可信度
- [ ] **T4** 指出回归防线的覆盖边界——哪些老行为有基线可依、哪些没有
- [ ] **T5** 为**本次不改、但与改动共用底层实现**的老路径写了拦截用例（例如新规则的报错逻辑若落进共享校验，会把老路径的容错行为顺手改坏）

## 判定

T2 与 T3 都以基线自带的回归防线清单为准。

**T2 是这条 case 的核心。** "让新行为对"是任何测试都会做的；"老行为不许变"是存量迭代专有的。

> **改 skill 时不要从本判据取词。** 判据与被判对象共用句子时，这条判据对那句话失去独立性。

**T3 考的是它有没有真的读懂可信度标签。** 用一条推断去卡住一次变更，等于把猜错的现状固化成需求——`source-intake` 的现状基线模板明令禁止 `INFERRED` 进回归防线，`test-authoring` 这一侧要接得住。
