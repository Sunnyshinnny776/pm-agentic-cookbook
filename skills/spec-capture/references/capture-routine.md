# 沉淀例程(8 步)

> 触发后按序执行。本例程是宿主 spec 加载规则(宿主契约 `host.specMap` 的 `loading-rule` 角色)中沉淀检查与沉淀流程的可执行版,并扩展沉淀目标到 cookbook。

## 第 1 步:圈定本阶段范围

- 用 `git diff`(自上次沉淀点 / 相关提交以来)+ 本次会话中**已确认的决策**和**用户的纠正**,列出"本阶段改了什么、定了什么"。
- 范围由调用方的参数或用户指定时,以其为准。
- 产出:一份"本阶段决策/改动清单",作为后续筛选的素材。

## 第 2 步:必要性判断(本阶段是否值得沉淀)— 前置 gate

在逐条筛选之前,先做一次**整体必要性判断**:本阶段/任务是否值得、有必要沉淀为 spec 或 skill。

判为**无需沉淀**(早退)的典型情形:
- 纯一次性页面内容、孤立文案、临时 mock 数据。
- 纯 bugfix / 重构,未引入任何新的、可复用的约定或边界。
- 探索性产出,用户尚未接受为正式决定。
- 本阶段的规则已在既有 spec 中覆盖,无新增或变更。

判断结果:
- **无需沉淀** → 如实输出"本阶段无可沉淀项"及简要理由,**到此停止**,不进入后续步骤。不为沉淀而沉淀。
- **可能有可沉淀项** → 继续第 3 步逐条筛选。

> 这一步是诚实闸门:宁可如实报"无需沉淀",也不强行制造低价值规则。

## 第 3 步:按捕获触发器筛选

命中**任一**触发器的,才是候选沉淀项(宿主的加载规则另有触发器时,一并适用):

- 就某条可复用的 UI / 交互 / 集成 / 工作流规则,达成了稳定决定。
- 引入了未来页面/模块应遵循的新模式。
- 实施中发现并解决了 spec 缺口。
- 多个文件/模块现在依赖同一行为或术语。
- 用户的纠正改变了既有规则、边界或命名约定。
- 引入了新的外部系统、工作流职责边界、回调、重试或状态映射。

**明确排除**(不沉淀):一次性页面内容、临时 mock、孤立文案改动、不太会复发的实现细节、用户尚未接受的想法。

## 第 4 步:分类路由

对每条候选项,按[规则归属路由图](routing-map.md)确定归属(宿主 spec 的某个角色 / 模块需求文档 / skill / process / templates / 宿主规则文件)。

## 第 5 步:去重与最小归属

1. 找到能**owning** 这条规则的最小既有 spec。
2. 已存在归属 → 在其中增补,沿用既有风格与术语。
3. 无既有归属 → **告知用户需要新建,并建议文件路径**;不擅自创建宽泛新文档。
4. 与既有规则冲突 → 标为"待确认",交用户裁定,不私自覆盖。

## 第 6 步:输出沉淀提议清单

以表格交付,**先提议、不落盘**:

| 编号 | 规则(拟沉淀) | 来源(本阶段哪次决策/diff) | 归属(文件 / skill) | 新增 or 增补 | 拟写文字(草稿) |
| --- | --- | --- | --- | --- | --- |

另列"待确认沉淀项"(拿不准是否可复用 / 与既有冲突)。

## 第 7 步:裁定后落盘

用户裁定后:

1. 将获批项写入归属文档,沿用其风格。
2. **若改动 skill 的 SKILL.md 或 references/**:用该 skill 的 `scripts/build.py` 重建 `dist/`(若有)。
3. 新建了 spec 文件 → 更新索引链接(`specMap` 中 `index` 角色的文档总索引,以及所在角色的总纲),并提醒用户在宿主契约的 `specMap` 里登记新文件(登记的是目录时不需要)。
4. 写入高冲突文件(UI/UX 总纲、宿主规则文件、依赖清单等)前再次确认;保持改动小、目的单一。
5. **不自动提交**:产生工作区改动即可,`git commit/push` 由用户另行授权。

## 第 8 步:报告

最终报告如实包含:

- 已沉淀项:规则 → 归属文件,是否重建 dist。
- 刻意未沉淀项及理由(一次性 / 不可复用 / 待用户接受)。
- 不下达"规则已收口 / 通过"的自我结论;是否收口由用户判断。
