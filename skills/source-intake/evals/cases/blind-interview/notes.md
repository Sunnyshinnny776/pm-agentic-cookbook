# notes：无文档盲测访谈

## 这个 case 守护什么

**`source-intake` 的核心主张是"没有 Oracle 就不接"；材料不足时，Oracle 靠访谈固化出来。** 本 case 检验这条访谈流程能不能把业务方脑子里的需求问出来。

方法论认定最有效的业务理解手段是观摩实习、轮岗、进入作业现场、与业务人员建立信任，并明确评价单纯读资料"非常有限"。执行者一项都做不到，只能做结构化提问。所以这条流程有没有效，**只能靠一次真实的盲测**。

## 为什么判据是这三条结论

A 组三条是计划任务的权限治理链、计划周期的主子结构、计划模板的集团管控框架。它们的共同点是**业务方不会主动说**——粗线条描述里根本不含这些层次，只有层层追问才会浮现。

选它们而不是选表层信息（有哪些页面、要哪些字段），是因为表层信息问不出来才叫失败，而**深层结构问不出来才是这套方法论真正的失效模式**。

## 污染约束

**编写 case 的人知道答案，因此不能当访谈者，也不能判卷。**

| 角色 | 谁 |
| --- | --- |
| 被试 | 干净目录里新开的会话，只装本 skill |
| 被访者 | 知道答案的人 |
| 判卷 | **独立冷启动子代理**，按固定判据核对访谈原文 |

判卷属审计类，按 `process/agent-execution-protocol.md` 派发，冷启动输入给全，**报告原样转呈不改写**。

被访者提示卡是必需品：没有它，知道答案的人会不自觉地把答案喂出去，测出来的是理想被访者下的表现。
