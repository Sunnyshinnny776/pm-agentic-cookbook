# 现状基线

> T3（存量迭代）档的产出。反向工程一个**已在运行的系统**，把"它现在到底是什么样"固化成可引用的文件。
> 迭代的 Oracle = **本基线 + 增量意图**。没有基线，变更需求文档就没有对照面，"老行为不许变"这条无从校验。
> **实现是「是什么」的权威，用户是「应该是什么」的权威，既有文档在两方面都不是最高权威。** 既有文档仍然可以当证据用，可信度按下方的证据梯度封顶。

## 二、现状描述

**每条结论必须带可信度标签与证据指针。** 可信度四级：`CONFIRMED` / `CORROBORATED` / `INFERRED` / `UNRESOLVED`，取值口径与准入报告一致。证据指针要能指到具体位置——文件与章节、页面与字段、数据导出的哪一列。"凭印象"不算指针。

**证据梯度决定可信度上限。** 拿不到实现的访问权是常态，**它不构成阻塞**，只影响这张表能标到多高：

| 证据来源 | 可信度上限 |
| --- | --- |
| 实现入口、数据结构 | `CONFIRMED` |
| 亲自在运行中的系统里核对过 | `CONFIRMED` |
| 真实业务数据导出 | `CONFIRMED`（限该数据覆盖到的字段） |
| 实现方口述 | `CORROBORATED` |
| 既有需求文档、原型、手册 | `CORROBORATED`；与其他证据互相印证后可升级 |
| 由已确认内容推导 | `INFERRED` |

**默认路径是文档基线**：既有需求文档、原型、截图、手册组装出现状，再用一份真实业务数据导出做抽样校验——抽样补的是文档天然写不细的那一层。**代码基线是加强档**，拿得到才走。

按模块分节，每节按四层展开（与准入报告的深度四层同构）。

## 三、三方冲突登记

实现、用户、旧文档三者不一致时，**不得自行择一**，全部进 UNRESOLVED 交人裁定。

| # | 冲突点 | 实现是什么 | 用户说应该是什么 | 旧文档写的是什么 | 裁定结果 |
| --- | --- | --- | --- | --- | --- |
| U-1 | {描述} | {证据指针} | {出处} | {出处} | {待填 / 已裁定为…} |

> 常见的三种形态：实现里有一条谁都不知道的隐藏规则；用户描述的是他**希望**的行为而非现行行为；旧文档停留在某个早已被改掉的版本。三者都不能单独当基线。

> 可信度为 `INFERRED` 的条目**不得直接进入回归防线**——用一条推断去卡住一次变更，会把"猜错的现状"固化成需求。先升级它的可信度，或列入未覆盖区域。

## 六、能力边界声明

本基线由 {人 / AI} 反向工程得出。以下限制在使用本文件时必须知晓：

- 本基线走的是 **{文档基线 / 代码基线}** 路径，可信度上限受此限制
- 基线反映的是 **{基线日期} 的 {版本号}**，此后的变更不在其中
- 标为 `INFERRED` 的条目是推导结果，**不是已确认的现状**
- 「未覆盖区域」列出的部分**没有基线**，涉及它们的变更需要单独确认
- 反向工程无法获得**设计意图**，只能获得实现结果；某条行为是有意为之还是历史缺陷，本文件不作判断
