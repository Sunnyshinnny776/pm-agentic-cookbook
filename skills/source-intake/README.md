# source-intake — 源材料准入

[English](README.en.md)

> **本 skill 不假装访谈产出就是权威需求。** 完备度矩阵显式区分「用户确认 / 执行者推断 / 仍空白」三态；AI 无法执行观摩、轮岗、进入作业现场这类现场手段，因此访谈产出是**待确认的需求草稿**。准入通过与否由人裁定，执行者不得自行宣告。

流程的**阶段零**：在建模、写需求文档、做原型之前，先判断手上有什么材料，据此决定后面各阶段的依据从哪来、哪些结论可以直接引用、哪些必须先问人。

## 它解决什么

后续每个阶段都以「存在一份质量足够的 Oracle」为前提：生成需求文档要有依据，审计要有比对基准，写测试要有预言。**这个前提从来不会自己报错**——材料缺失时，各阶段照常产出看起来完整的文档，只是那些文档没有判据。

本 skill 把这个前提变成一次显式检查，并给材料不足与存量迭代两种场景铺降级路径。

## 核心裁定

**Oracle 必须存在，且必须是文件。** 差别只在它从哪来——用户提供的文档、访谈固化成的确认书、或从运行中的系统反向工程出的基线。没有 Oracle 的项目不接。

口头共识不能被 diff、不能被引用到行、不能在下一轮会话里被核对，而下游三类工作全部依赖"能指到某一行"。

## 四问与四档

**准入四问**：可读性 → 权威性 → **完备性（广度 × 深度）** → 一致性。四问全部有结论才进入档位判定。

其中完备性分两维：**广度**是覆盖哪些模块，**深度**是每个模块讲到哪一层（业务流程 / 业务规则 / 字段与取值 / 异常与边界）。深度是最容易出问题的一维，范围蔓延多数由双方对深度理解不同而来。

**四档**：T0 对话式（无文档）、T1 轻量（零散材料）、T2 完整（成体系文档）、T3 存量迭代（已有运行中的实现）。档位只决定 Oracle 来源，不裁剪后续流程：每一档都走数据建模 → 需求文档 → 审计。

## 产出

《源材料准入报告》、《源材料索引》（后续所有阶段查阅材料的唯一入口）、《需求确认书》（T0/T1）、《现状基线》（T3）。

阶段零逐项整理候选需求范围与交叉依赖，初步确认后交建模验证；标准生成前才最终确认。范围可以跨模块、关联多模型/PRD，模块只索引，不能按文件数猜归属。

## 能力边界

- **能守住的：行为约束与访谈方法。** 不自行宣告准入通过，不把执行者的推断标成用户确认，摊开前提假设，不把做不到的事推给用户；从动因倒推，不问预测性问题，访谈规模与变更粒度相称。
- **不保证的：深层需求挖掘。** 业务方不会主动说出的深层结构——多层级的授权链条、周期的主子结构、上下级之间的管控框架这一类——访谈未必问得出来。**不要期待它把口述需求问成可以直接引用的深层业务模型**：访谈产出是待确认的草稿，深层结构仍要靠人追问和确认。
