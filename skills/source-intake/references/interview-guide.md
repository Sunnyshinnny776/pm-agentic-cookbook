# 结构化访谈指引

> 方法论基础：《决胜B端》三层业务调研框架与五环节调研法；《决胜体验设计》第 3 章用户调研的方式与技巧、第 4 章场景识别与用户旅程。
>
> 适用档位：T0（无文档）与 T1（材料零散）。T2/T3 不走本流程，但其缺口清单的追问同样适用本文的提问技术。

---

## 零、执行者的四条硬约束

写在最前面，因为它们决定了下面所有技术的使用边界。

1. **不得替用户做需求分析。** 本流程产出的是待确认草稿，权威性由用户确认赋予，不由完整度赋予。
2. **不得让用户预测自己的行为。** "这个功能你会用吗"这类问题的答案不可信——普遍的经验是多数人回答"会"，上线后无人使用。要问已发生的事实，不问未来的意向。
3. **完备度矩阵必须三态分明**：用户确认 / 执行者推断 / 仍空白。推断项与空白项不得当作已确认内容进入下游。
4. **声明能力边界。** 最有效的业务理解手段是观摩、轮岗、进入作业现场、与业务人员建立信任，执行者一项都做不到；单纯读资料被方法论明确评价为"非常有限"。因此本流程的产出完备性天然低于人工调研，**必须在报告中写明**。

## 一、五步骤骨架

```
① 明确调研目标 → ② 选取调研对象 → ③ 确认调研方法 → ④ 执行调研计划 → ⑤ 总结归纳输出
```

用 5W1H 落地：

| 步骤 | 对应 | 要点 |
| --- | --- | --- |
| 明确目标 | **why** | 是把线下流程线上化，还是解决具体的管理/经营问题？后者要问清是哪一类：管控模式、合规风控、行业监管、经营策略 |
| 选取对象 | **who** | 按三层选人，见第三节 |
| 确认内容 | **what** | **最难的一步**。按对象层级组织问题清单，事前准备，不临场发挥 |
| 制定计划 | **when / where** | 时间、场合、时长；材料提前送达 |
| 执行与收口 | **how** | 控场与节奏，见第五节；结束后整理确认，见第八节 |

**这份清单会随使用变厚。** 每做一次访谈，把当次"如何思考问题清单"的过程记下来，几轮之后就形成了自己的领域访谈清单。

## 二、四个目标与本 skill 的边界

调研目标按产品生命周期分四类：

| 目标 | 时机 | 最有效手段 |
| --- | --- | --- |
| **了解业务** | 设计前期 | 观摩实习、深度访谈（建立直接认知）；问卷、数据分析、行业研究、同类产品分析作为广度补充 |
| **挖掘问题** | 需求阶段 | 轮岗实习 + 一对一深度访谈 |
| 评估方案 | 设计完成、投入开发前 | 与原始提出人及利益方一对一确认；可用原型试用或焦点小组 |
| 上线反馈 | 上线后 | 访谈、问卷、观察、行为数据分析 |

**本 skill 只覆盖前两个。** 「评估方案」归需求文档审计环节，「上线反馈」归走查与迭代环节。**不要在准入阶段做方案评估**——那时还没有方案。

## 三、三类对象各问什么

对齐三层业务调研框架。三类人关心的东西不同，同一套问题问下去只会得到三份雷同且都不深的答案。

### 先定谁入场：由变更粒度决定，不由材料体量决定

**三层不是每次都要走满。** 一份材料描述了整个子域，不代表这次要做整个子域——按材料体量安排场次，会为一条规则组织多场跨部门访谈。

| 粒度 | 谁入场 |
| --- | --- |
| **功能点级**（一个页面、一条规则、一个字段） | 需求提出人 + 实现方，两次短对话，**不组织多方访谈** |
| **模块级** | 战术层 + 执行层 |
| **系统级 / 从零立项** | 三层走满 |

**战略层的入场条件要单独说**：系统级的战略动因在从零立项的阶段就该定下来了。到了模块级与功能点级还去问"为什么要建这个"，多半会逼着受访人现编一个理由。除非本次变更确实改变了系统边界或商业模式，否则不单独安排战略层场次。

安排之前先判**撑不撑得起**（有没有多个立场可能不同的利益相关方、有没有未知的业务流程）与**值不值得**（是否绝大多数问题能从已有材料或现有实现回答）。两条都不成立时降级为一次澄清对话。

### 问题清单分两栏

列问题时强制分开：**可从已有材料或现有实现回答的** / **必须问人的**。只有后一栏进访谈提纲。访谈时间是别人的，能自己查到的不占用。

| 层 | 关心什么 | 提问方向 | 常见障碍 |
| --- | --- | --- | --- |
| **高层 / 战略层** | 系统的实现范围、能带来的回报 | **先找到触发他想建系统的原因**：外出考察见到的做法、竞争对手动向、新技术或新渠道带来的压力、上层规划中的位置 | 多数项目**访谈不到高层**。此时从立项文件、招标材料、上层战略规划中提取目标与背景 |
| **中层 / 战术层** | 通过系统能解决什么管理问题或业务问题 | 管理动作与考核口径、跨部门协同的断点、当前靠什么手工手段兜底 | 容易把管理诉求说成功能诉求，要往回追 |
| **执行层** | 具体操作层面的问题 | 一天的作业流程、卡在哪里、有没有绕过系统的私下做法、哪些步骤要重复录入 | 可能不愿暴露绕过系统的做法，需要先建立安全感 |

## 四、提问技术

### 开放式与封闭式

| 类型 | 用途 | 例 |
| --- | --- | --- |
| **开放式** | 让对方发散、多描述，尽可能多地提供信息 | "这个模块的业务流程具体是怎样的？""平时工作中最麻烦的是哪一步？" |
| **封闭式** | 在已获信息上做确认，让对方答"是不是/有没有"，**校验自己的理解有没有偏差** | "所以这一步是先审批再录入，对吗？" |

结合目的选择，不是先开放后封闭的固定顺序。

#### 每个话题的第一问必须是开放式

封闭式问题——包括把候选答案列成选项让对方挑——**只能用在对方已经说过的内容上**，用途是校验理解有没有偏差。

判据只有一句：**这个选项里的内容，对方说过吗？**

| | 做法 |
| --- | --- |
| 说过 | 可以列成选项请他确认。这是封闭式的本职 |
| **没说过** | **必须开放式。** 把自己的领域先验写成选项让对方点选，拿到的是他对你的模型的追认，不是他的业务 |

这条防的是一种看起来很高效的失败：执行者凭行业经验把常见模式写成几个选项，对方从里面挑一个，双方都觉得问清楚了。**但真正发生的是执行者替对方描述了他的业务**，而对方只是认可了一个听起来对的说法。这类结论在报告里与真实调研所得无法区分，且往往在实现阶段才暴露不符。

它同时架空了下面那条最核心的规则：对方没机会抛出自己的解决方案，也就无从往回追真实意图。

#### 带"推荐"的选项，只用在工程后果上

**判据：这件事谁更有资格判断？**

| | 做法 |
| --- | --- |
| **业务事实**（现在怎么算的、谁能看谁的数据、有几类用工） | 对方是权威，执行者没有立场推荐。**不给推荐，也不给选项** |
| **工程后果**（双轨要跑几个薪期、四套算法赶不赶得上这个工期） | 执行者有依据，**可以给推荐，但必须同时给出依据**，让对方能反驳依据而不只是反驳结论 |

#### 默认值同理，且"带理由的倾向"算默认值

**默认值不得在数据可见性、权限、留痕、金额精度这类问题上偏向省事**——这几类的"默认不做"会把风险悄悄留在系统里，而对方往往顺着默认值点头。

判据：**这个默认值若被顺手接受，出错的代价由谁承担？** 代价落在提问者这一侧（少写一个字段、少做一个页面）可以给默认；代价落在使用者或数据主体那一侧（谁能看到谁的数据、错了能不能查），**必须问开放式，让对方自己说**。

**在这几类问题上，给"执行者倾向"与给默认值是同一件事**，哪怕附了理由。待裁定项后面挂一句"我的建议是按某某切分"，对方多半会顺着它裁定——**它省掉的正是本该由他做的那次判断**。这类条目只列候选与各自代价，不列倾向。

### 两种提问顺序

- **金字塔顺序**：从一个点逐步发散，铺开面
- **漏斗顺序**：从开放式提问开始，逐步聚焦到具体功能，收敛成结论

一次访谈里两种交替使用：新话题用金字塔铺开，要落结论时切漏斗收口。

### 最核心的一条：对方给的是解决方案，不是需求

**用户提出的几乎总是他想到的解法，层层追问才会露出真实意图。** 知道真实意图后往往存在多个解法，再综合成本与收益选最合适的那个。

对执行者尤其重要：**AI 天然倾向于直接接收并实现被描述的方案**。听到"我要一个导出按钮"就去做导出按钮，而没有问"导出之后你拿它做什么"。

追问用 5W 逐层下探，直到能回答"他到底想干什么"。

## 五、握节奏：六条可直接照做的

1. **访谈计划与问题清单提前送达**，让对方有时间准备资料。
2. **尽量当倾听者**，对方能说就让他说，不打断；问题要短，不用拗口或有歧义的表述。
3. **循环提问**：封闭（判断题）、半封闭（选择题）、开放式三种交替。
4. **准备图形和表格**——沟通效率排序是 **图形 > 表格 > 文字**。复杂业务尤其要用图讨论，能大幅减少理解偏差，而且同一张图确认完可以直接给下游用，一次工作两次生效。
5. **对业务术语做功课**，事前了解行业惯用语，不要在访谈中现学。
6. **对着清单查漏**，确保不遗漏事先定好的问题。

前提是功课做够：至少对业务有一个大致了解，而不是一点都不懂。

## 六、场景还原

需求脱离场景就无法判断合理性。用 **5W1H** 或六要素还原：**人物、时间、地点（含环境）、起因、经过、结果**。

**必须找到原始需求提出人**，不接受二手转述——转述会抹掉需求的特殊性，让合理需求看起来不合理。

> 典型案例：一线人员提出"希望把新任务提醒的字号调大"。听起来不合理——不是有语音播报吗？于是被打回。找到原始提出人还原场景后：**该人员有听力障碍**，语音播报对他无效，需要清晰的文字提示才能及时准确接收任务。需求的特殊性与合理性只有在场景中才显现。

### 识别场景的三个价值

1. **追本溯源**：只把线下流程搬上线，会失去改进业务的机会；进入问题发生的场景才能从源头分析。
2. **让体验优化有落点**：明确场景 → 展开用户旅程 → 分析每个节点的诉求、痛点、机会点。离开场景，体验无从谈起。
3. **迫使调研者进入一线**：和用户走在一起才能真正理解业务。

### 这类产品的场景比消费级发散

消费级产品场景收敛（围绕一件事的前中后即可覆盖核心）。**企业级产品不能只分析与软件相关的场景，要全面了解用户的全部工作**——同一个岗位的工作之间往往没有明显相关性，即便你负责的模块不涉及某项工作，也应掌握，否则会误判。

小组织中一人身兼多职时，梳理要灵活取舍。

## 七、数据类需求的额外必问项

涉及上下游流转的数据类需求，只拿到样表和字段是不够的，必须补问：

- **数据用途**：这个字段拿来做什么
- **数据来源**：谁产生、什么时候产生、来自哪个环节
- **计算规则**：派生字段的公式、口径、取数时点
- **表单之间的关系**：流程上涉及多张表单时，理清它们如何关联、谁是主、谁是从

并且**先统一业务术语**——不同团队术语不一致时，字段对不上往往是叫法问题而非结构问题。

## 八、材料不足或对方难约时的四条路径

1. 请对方**先提供书面资料**，用来理清基本概念与业务常识
2. **查阅体系化的专业资料**，比零散讨论更容易建立框架
3. **请教有经验的人**，问常见问题与常见坑
4. **看同类产品怎么做**，找差异点

共同的前提是：**先自己做够准备，带着知识储备和整理好的问题清单再去沟通。**

沟通一轮之后：把**已确认的内容整理出来、标出重点、发回对方确认**，再约后续讨论。这一步不能省——它是把"聊过"变成"确认过"的唯一动作，也是完备度矩阵中"用户确认"一态的来源。

## 九、收口：完备度矩阵

访谈的最终产出是《需求确认书》加一张完备度矩阵。矩阵按模块 × 层次（业务流程 / 业务规则 / 字段与取值 / 异常与边界）铺开，每格标注三态之一：

| 标记 | 含义 | 下游怎么用 |
| --- | --- | --- |
| **用户确认** | 经过第八节的"整理—回执—确认"闭环 | 可作为 Oracle 引用 |
| **执行者推断** | 由已确认内容推导，未经确认 | **不得作为规则来源**，需在下游标注 |
| **仍空白** | 未覆盖 | 进缺口清单，是"停下问人"的触发点 |

矩阵中"仍空白"与"执行者推断"占比过高时，**如实说明该确认书尚不足以支撑下游工作**，而不是补齐格子让它看起来完整。
