# 档位判定

> 档位决定 Oracle 的来源，不裁剪后续流程——每一档都走数据建模 → 需求文档 → 审计，产出多厚随本次变更的大小。判定结论写进《源材料准入报告》，**由用户确认后才生效**。

---

## 判定树

```
有没有已在运行的实现？
├─ 有 ────────────────────────────────► T3 存量迭代
└─ 没有
   └─ 有没有成体系的方案或系统级需求文档？
      ├─ 有 ─────────────────────────► T2 完整
      └─ 没有
         └─ 有没有零散材料（截图/表格/口述记录）？
            ├─ 有，且范围限于单模块 ──► T1 轻量
            └─ 几乎没有
               └─ 需求能否一次对话说清（单页面/单功能）？
                  ├─ 能 ─────────────► T0 对话式
                  └─ 不能 ───────────► 不接，先补材料
```

**最后一个分支是硬停机点。** 需求说不清且没有材料时，不存在可行的降级路径——继续下去只会产出没有判据的文档。此时的正确动作是把缺口清单交给用户，等材料或等一次能说清的范围。

---

## 另一根轴：变更粒度

档位回答的是「Oracle 从哪来」。它**不回答「这次要交付的东西有多大」**，而后者决定投入多少人力去问人。

两根轴必须分开判，否则会出现一种典型的过度投入：材料描述了一整个子域，实际要做的只是其中一个功能点，而访谈规模跟着材料体量走，最后为一条规则组织了多场跨部门访谈。

| 粒度 | 判据 |
| --- | --- |
| **系统级** | 新建一个系统，或接手一个此前完全不了解的系统 |
| **模块级** | 一个完整业务模块的新建或重构 |
| **功能点级** | 一个页面、一条规则、一个字段，嵌在已经在跑的流程里 |

粒度由**本次要交付的变更**决定，与材料的体量无关。

### 粒度判定的输出形态

**信息不足时粒度会系统性上偏**——材料描述了整个子域，判定就跟着往上走。而粒度取决于变更在目标系统架构里的位置，**那是用户知道、执行者不可能知道的信息**。

所以粒度不能只给一个结论，必须同时给出**可逐条否掉的边界**：

| 输出 | 内容 |
| --- | --- |
| **范围内** | 本次要交付的能力，逐项列出 |
| **范围外** | 执行者**假设**不包含的部分，逐项列出并注明假设理由 |
| **具名前提假设** | 支撑这个范围划分的关键前提，给它一个编号，写明**它不成立时会怎样** |
| **验证方式** | 指定一份材料或一次提问来验证该假设 |

把假设摊开，比把假设猜对更重要。用户扫一眼就能改一行，而执行者本来就没有条件猜对目标系统的架构。

### 访谈规模由粒度决定

| 粒度 | 访谈形态 | 典型投入 |
| --- | --- | --- |
| **功能点级** | 两次短对话：向需求提出人问「应该是什么」，向实现方问「现在是什么」。不组织多方访谈 | 2 人 × 30 分钟 |
| **模块级** | 战术层 + 执行层两场 | 2 场 |
| **系统级** | 三层完整走 | 3 场以上 |

**物料先行能压缩访谈规模。** 先补材料再编提纲，原本要问人的问题会有相当一部分落进"可从材料回答"那一栏。所以物料清单与访谈提纲有先后：**先出物料清单，材料到位后再编提纲**，而不是两件事并行。

### 战略层是否入场，也由粒度决定

系统级的战略动因在 0 到 1 的阶段就该定下来了。到了模块级与功能点级，再去问战略层"为什么要建这个"，多半会逼着受访人现编一个理由。

- **系统级 / 从零立项**：战略层必须入场，问不到就从立项文件、上层规划中提取
- **模块级 / 功能点级**：默认不单独安排场次；若本次变更确实改变了系统边界或商业模式，按系统级处理

## 撑不撑得起，与值不值得

访谈的成本落在真人身上，且不可回收。安排之前分开判两件事：

| 判什么 | 不成立的表现 |
| --- | --- |
| **撑不撑得起** | 只有一个利益相关方；业务流程是现成的、这次并不改；没有立场分歧可言 |
| **值不值得** | 绝大多数问题能从已有材料或现有实现回答，只有少数几条需要人裁定 |

两条都不成立时，降级为**一次澄清对话**，产出一份变更需求确认书即可。

## 四档对照

| | T0 对话式 | T1 轻量 | T2 完整 | T3 存量迭代 |
| --- | --- | --- | --- | --- |
| **触发** | 无文档，一次对话可说清 | 零散材料，单模块 | 成体系文档，多模块 | 已有运行中的实现 |
| **Oracle** | 访谈固化成的《需求确认书》 | 《需求确认书》 | 用户提供的文档 | 《现状基线》 |
| **需求文档形态** | 需求文档 | 需求文档 | 需求文档 | **变更需求文档**，审计审变更的完备性 |
| **范围收敛起点** | 加法模型 | 加法为主 | 减法模型 | 减法为主 |

---

## 范围收敛的两个模型

| | 加法模型 | 减法模型 |
| --- | --- | --- |
| **做法** | 先限定成本、时间、质量三个约束，再像搭积木一样逐步增加功能与范围 | 把已有材料要求的工作梳成清单，明确三约束，由粗到细厘清模糊部分，把超出边界的逐步裁掉 |
| **适用** | 材料宽泛、需求不清晰 | 已有成体系材料 |
| **风险** | 容易越搭越大，需要三约束持续把关 | 容易把模糊的部分整块裁掉，实际是没问清 |

**实际工作中两者共同使用**：先用减法从材料裁出主干，再用加法把访谈补出来的部分搭上去。最终勾勒出的是"**相对准确**"的范围——承认它不精确，比假装精确更有用。

## 档位不是一次性的

材料在过程中会变化：用户可能补交文档（T1 升 T2），也可能发现所谓的"完整文档"其实只覆盖两个模块（T2 降 T1）。

**档位变化必须重新走准入四问并更新报告**，不能沿用旧判定继续。

## 需求范围组织

用户一次输入可含多个交叉需求。执行者逐项对照原始要求，整理候选范围与未决边界，不要求用户先拆好，也不因尚未实现而删除要求。范围以明确业务结果和有意义的验收出口划分，包含/排除、依赖契约及就绪条件须可说明；页面、模块名、文件数量和开发分工不能单独决定分组。

复用《需求确认书》或已有模块/项目入口的范围表：`范围名称｜业务结果｜包含与排除｜依赖与交叉｜验收出口｜确认状态`。各范围有独立结果时分别组织；共同支撑一个不可拆业务结果时保留一个跨模块范围；有独立结果又有共同端到端要求时，另提仅覆盖共同条件和交互结果的集成验收范围，引用共享契约，不复制子范围标准。边界不足以判断时给出推荐方案与取舍，请用户确认。

阶段零只确认初步边界。建模验证后，生成验收标准前由用户确认最终范围；已有一次确认明确包含模型和最终范围时不重复询问。跨模块范围须确认主归集位置与协调责任方，其余入口只引用。每个最终范围对应一份标准清单及一份验收台账，模块只作索引；范围可关联多份模型/PRD，共享模型可供多个范围使用。本阶段不生成标准或宣告交付已验收。
