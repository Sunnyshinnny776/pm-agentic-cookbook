# 一致性审计

回答一件事：**X 是否按 Y 说的那样成立。** Y 是 Oracle——规则、需求、裁定、模型、目录；X 是被核对对象——代码、另一份文档、图示、测试规格、代码里的目录镜像。

两个对象之间的每一处不一致，要么是实现的缺陷，要么是文档该改，判定是哪一种就是发现本身。单个对象写得好不好不在本 skill 的范围内。

**执行者与上下文隔离**：本 skill 属审计类。当前 Agent 若是任一被核对对象的作者，必须委派独立执行者运行本 skill，并原样转呈报告。审计结论是呈给用户裁定的证据，任何执行者都不得宣告"一致、可推进"。

**审计权限**：对全部被核对对象只读；不删除、不标记其它审计报告，只写本次报告。允许写临时探针用例或做变异核验，但必须在结束前全部还原，并在报告里写明还原的核验方式。

## 验收标准的核对范围

核对验收清单与PRD、旅程覆盖清单、测试时，以范围内已确认条目为Oracle，按“清单名称 AC-n”连接各对象，并核对来源章节与版本、逐条覆盖和新增/冲突的业务结果。未确认/作废行不可当生效要求；只有裸编号、复制主表形成第二权威、来源版本不同或只命中同一章节均不能证明一致。反查下游独有预期，记录应回改的最上游对象。

本skill仍只读被审对象、输出报告；回改和用户确认由拥有修改授权的作者承担。

核对交付验收台账时，Oracle包括最终确认的需求范围、有效标准及版本；对照实现/测试/旅程实际断言与台账的适用行、结果、证据基线、未覆盖项及用户裁定来源。满足须覆盖全部必要适用路径；部分满足须同条标准有成功和失败，单有成功/未知为证据不足，确定失败不能隐藏。核销仅限满足且用户明确通过的版本/范围；偏差/延期/作废不计满足。集成出口单独查证，旧版本或Mock/单元证据不证明真实新集成。反查无标准行为与漏行，不代写台账或替用户验收；六种一致性判定保留，与台账四种事实结果分别使用。

## 输入

- **Oracle**：逐个文件路径。多份 Oracle 之间冲突时，冲突本身记为发现，不自行选一个信
- **被核对对象**：逐个文件或目录路径，并注明对象类别（代码、文档、目录、图示、测试规格）
- **审计动作**：独立审计 / 定向复审 / 完整重审（见 [审计动作与报告](references/report-format.md)）
- **范围声明**：本轮不核对的对象类；复审时还有派发方给出的该对象全部未关闭条目（来自模块的问题登记表）
- 缺任何一项时，先向派发方或用户要，不自己去找被核对对象——范围由派发方定。无法询问时（无交互的单独使用），按最小合理假设执行，并在报告开头列出缺了哪项、按什么假设执行

## 工作流程

### 第一步：拆条目

把 Oracle 拆成**逐条可判定**的条目：一条只含一个断言，写明原文、出处（文件与行号）。可判定的断言通常落在：取值与集合（枚举值、权限点、角色列表）、计数、状态迁移与前置条件、约束（唯一、必填、不可删除、至少保留一个）、边界值、错误结果、跨对象的同一个名字或同一个数。

描述性文字、路线图与"未来可能"不拆成条目。Oracle 声明为目标态、且已登记了过渡形态的，只拆可与当前实现比较的步骤，其余列入未核对并注明"目标态"。拆出的条目太多时，按后果排序，**高后果（预估 P0/P1）的全部核对**，其余在报告里列为"未核对"，不许悄悄略过。

**一个条目要对照几个被核对对象，就拆成几行**，每行一个判定。

### 第二步：为每条找全实现侧的位置

**这一步决定审计质量。** 只找到一处实现就下结论，是最常见的漏审形态：规则在一条路径上成立，在另一条路径上失败。

- **代码**：列出**能改变该状态的全部入口**——所有写这个字段、改这个状态、增删这个集合的函数、页面动作与迁移脚本，逐一核对。检索方式写进记录：搜了哪些字段名、状态值、函数名，在哪些目录，各命中几处
- **文档**：同一个名字、同一个数在所有被核对对象里出现的位置全部列出，逐处比对
- **目录与其代码镜像**：用脚本抽取双方的集合与字段做差集，不靠目读

### 第三步：逐条判定

每条给出六种判定之一，定义与证据要求见 [判定与严重度](references/verdicts.md)：

| 判定 | 含义 |
| --- | --- |
| **部分成立** | 在一部分路径或位置成立，在另一部分不成立 |
| **相悖** | 实现与条目直接矛盾 |
| **缺失** | 找不到任何实现。**必须附检索记录**，没有检索记录的"缺失"无效 |
| **强于规定** | 实现施加了条目没有的限制，今天能用，但没人知道它存在 |
| **无法判定** | 条目本身含糊到无法核对——这是对 Oracle 的发现 |
| **成立** | 全部路径与位置都成立，列出核对过的每一处 |

**「部分成立」排在报告最前面。** 它通常是最严重的一类：常测的路径成立，所以它活得最久。

判定只用这六个，不加限定语（"成立（仅限某路径）"这类写法就是"部分成立"）。**实现可能位于被核对范围之外的条目，不判"缺失"**，列入未核对清单并写明原因。

### 第四步：反方向

实现里有、Oracle 没写的行为单列一节：代码里的额外校验、额外状态、额外权限，文档里多出来的规则。它们不一定是缺陷，但下一个改动的人不知道有东西依赖它。

核对过程中顺带看到的单个对象自身缺陷，**能关联到任一条目的，进判定表**；确实与所有条目都无关的（如编号生成会重复），单列为"附带发现"，同样定级。它们不在本 skill 的标准内，列出是为了不瞒报。

### 第五步：选取证方法

每条判定用什么证据，按 [取证方法](references/evidence-methods.md) 选。以下情形**必须**用可执行的证据，不能只凭读：

- 判"成立"的条目，其守护测试的期望值由被测对象同源生成——做变异核验
- 判"部分成立"或"相悖"的代码条目——写探针用例复现，并在结束前删除
- 目录与镜像的比对——用脚本做差集，报告附命令与输出

### 第六步：出报告

按 [审计动作与报告](references/report-format.md) 输出：元信息（含条目核销表）、条目判定表、反方向、附带发现、未核对清单。每条非"成立"的判定都要有证据定位（文件与行号）、复现方式与后果。

## 要拒绝的借口

| 借口 | 应对 |
| --- | --- |
| "找到实现了，规则成立" | 列出能改变该状态的全部入口再判；只核一处的判定无效 |
| "测试全绿" | 测试只证明它测的那条路径；看断言的期望值从哪来 |
| "文档写得很清楚，不会有问题" | 写清楚不等于做到；本 skill 核对的正是二者之间 |
| "这段早就有了，不是本次改动" | 在被核对范围内就要核；是否本次引入写进发现，不决定核不核 |
| "搜不到，应该是没实现" | 附上搜了什么、在哪、结果如何；执行常藏在调用方、基类或中间层 |
| "两份文档说法不同，以新的为准" | 冲突本身是发现，交用户裁定 |

## 停机条件

同时满足才算完成：

1. 高后果条目全部有判定；其余条目有判定或列入"未核对"
2. 每条"缺失"都有检索记录；每条"部分成立""相悖"都有证据定位与复现方式
3. 临时探针与变异已全部还原，并写明核验方式
4. 报告元信息齐全

**停下交用户**：Oracle 之间冲突，且多数高后果条目因此无法判定；被核对对象无法读取或与声明的快照不符。

**不自行宣告一致或通过。** 是否修复、修哪一侧、是否复审，由用户决定。

## 领域补充规则

领域由调用方显式给出，本 skill 不从被核对对象的内容里猜。调用时指定了领域，且 `references/providers/<domain>/` 下有对应 Provider，就额外加载它；没有指定时按通用方法执行，并在报告开头声明"未加载领域补充规则"。
